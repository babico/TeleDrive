## issue_api_key — POST /api/v1/admin/keys

- **Handler:** web/app.py:1860 (route declared web/app.py:1859-1883)
- **Auth model:**
  - **Session cookie principal:** must hold role `admin`. The path is in `_ADMIN_ONLY_PREFIXES` (web/permissions.py:76-79) so `is_admin_only()` (web/permissions.py:110-126) returns true for every method; `_required_roles` therefore returns `_ROLE_ADMIN` (web/app.py:524-525) and a `viewer`/`operator` session gets 403 before the handler (web/app.py:531-536). The permission map is a second gate, but every admin-only route is excluded from operator/viewer (web/permissions.py:316-330), so the path gate is the binding one.
  - **Bearer API-key principal:** `require_auth` only enters the key branch for `Bearer td_live_…` (web/app.py:575) and passes iff `permission_registry().permission_for("POST", path)` is `post:/api/v1/admin/keys` **and** the key is active and holds that permission (web/app.py:577-604). `admin:*` does **not** unlock this route: it expands only to the nine `ENDPOINT_PERMISSIONS` (teledrive/api_keys.py:60), so an `admin:*` key gets 403 here (asserted in tests/web/test_rest_api.py:127-132).
  - **Delegation ceiling:** a bearer caller may only request scopes whose expansion is a subset of its own effective scopes (`_delegation_limit`, web/app.py:1828-1840; `_require_within_delegation`, web/app.py:1843-1856). Session callers are unrestricted (`limit is None`).
  - **CSRF / same-origin:** `_same_origin` (web/app.py:300-312, called at 1861) requires the `x-teledrive-csrf: 1` header and, when `Origin` is present, an exact match to `Host`. It applies to bearer callers too (asserted tests/web/test_per_route_permissions.py:97-98).
  - **Host gate / body bound:** trusted-host middleware (web/app.py:1243-1250) and the JSON body-size middleware (web/app.py:1281-1297) run before routing.
- **Inputs:**
  - `name: str`, `Field(min_length=1, max_length=120)` (web/app.py:1350). Pydantic enforces 1..120 characters on the raw value; `ApiKeyStore.create` additionally strips and re-checks `1 <= len(name.strip()) <= 120` (teledrive/api_keys.py:122-123), so an all-whitespace name is a 422 from the store, not from the model. No charset restriction: newlines, NUL and other control characters are accepted and persisted. Stored stripped; logged **unstripped** (web/app.py:1868).
  - `scopes: list[str]`, `Field(min_length=1, max_length=20)` (web/app.py:1351). Each entry must be a `str` in `ALLOWED_SCOPES | catalog` where the catalog is every canonical `method:path` permission from the live route table plus the nine curated REST names (teledrive/api_keys.py:99-108; web/app.py:1874-1878). Duplicates are silently deduped by `sorted(set(...))` (teledrive/api_keys.py:109). `admin:*` may not be combined with anything else (teledrive/api_keys.py:110-111). The 20-item bound is on the raw list, so it does not bound effective scopes.
  - `expires_at: int | None` (web/app.py:1352). Pydantic lax mode coerces `true` → `1` and numeric strings; floats with a fraction are rejected. The store requires `now < expires_at <= now + 10*365*86400` (teledrive/api_keys.py:125-126). `None` means never expires. No timezone concept (Unix seconds), no grace, no relation to the caller's own expiry.
  - Unknown body fields are silently ignored (no `extra="forbid"`, no `response_model` on the route), e.g. `{"role": "admin", "id": "pwn"}` is accepted and discarded — verified.
- **Side effects:**
  - One `INSERT` into `api_credentials` with a 32-hex id, SHA-256 digest, 16-char prefix, stripped name, JSON scope list, `created_at`, `expires_at`, `last_used_at=NULL`, `revoked=False` (teledrive/api_keys.py:127-134), followed by `db.commit()` (teledrive/api_keys.py:135). Single statement + single commit, so no partial write is possible.
  - `ApiKeyStore(conn)` construction runs `ensure_schema(db.engine)` and `db.release_setup_snapshot()` on the request connection (teledrive/api_keys.py:92-96).
  - Audit: `_log(f"issue api key: name={payload.name} scopes={payload.scopes}", "api-keys")` (web/app.py:1868) — written **before** the store call, with the default `user="system"` (web/app.py:233-237), and without the new key's id or prefix. A second, framework-level line `POST /api/v1/admin/keys from <ip>` with `user=<key name or username>` is emitted by `_audit_log_middleware` (web/app.py:1253-1271 via `_extract_user`, web/app.py:214-229).
  - The plaintext token appears only in the 201 body. `Cache-Control: no-store` is applied to all `/api/` responses (web/app.py:1326-1329). The token is not logged and not returned by the list endpoint (teledrive/api_keys.py:138-145).
- **Failure modes:**
  - 401 — no session and no bearer credential (web/app.py:614-618).
  - 403 — bearer key invalid/expired/revoked or lacking `post:/api/v1/admin/keys` (web/app.py:599-604); session role not `admin` (web/app.py:531-536); missing `x-teledrive-csrf` or cross-origin `Origin` (web/app.py:300-312); requested scopes exceed the caller's own set (web/app.py:1849-1856).
  - 422 — Pydantic: `name` type/length, `scopes` type/list length/entry type, `expires_at` fractional float (web/app.py:1349-1352). Store `ValueError` re-emitted verbatim as `HTTPException(422, str(exc))` (web/app.py:1879-1880): whitespace-only name, empty/unknown/non-string scope, `admin:*` mixed, expiry in the past or beyond 10 years.
  - 413 — body over `MAX_REQUEST_BYTES` (web/app.py:1288-1296); 400 — invalid `Host` (web/app.py:1247-1249).
  - 500 — any `SQLAlchemyError` (e.g. `IntegrityError`, DB down) escapes the handler: nothing catches it (web/app.py:1871-1883). Verified with an injected `IntegrityError`: the client receives a bare `Internal Server Error`, and the middleware writes the full statement and bound parameters into `LOG_BUFFER` (web/app.py:1266), which `GET /api/v1/logs` serves unredacted to a `viewer` (web/app.py:3269-3285).
  - No 429 / rate limit on issuance; no 409 path (name is not unique).
- **Findings:**
  - [high] **The delegation ceiling constrains scopes but not lifetime or lineage.** `_require_within_delegation` is passed only the expanded scope set (web/app.py:1866-1867) and `payload.expires_at` goes straight to the store (web/app.py:1877). Verified: a key holding only `post:/api/v1/admin/keys` with `expires_at = now+60` minted a child with **no** expiry and a child expiring in nine years (both 201), and the child kept minting after the parent was revoked (201). So an expiring, revocable key can plant permanent, non-revocable descendants holding the same authority. The docs treat "the power to mint keys" as an owner decision (tests/web/test_per_route_permissions.py:92-93), but the owner has no way to recall it.
  - [medium] **The issuance audit record has no actor and no credential identifier.** `_log` defaults to `user="system"` and the call passes no `user=` (web/app.py:1868 vs the pattern at 1783-1785, 1953). The line also omits `id`/`prefix`, so it cannot be joined to the `api_credentials` row, and names are not unique (no unique constraint, teledrive/api_keys.py:20-31), so two keys named "backup" are indistinguishable; revoke/rotate log the id (web/app.py:1896, 1914), issue does not. Partial mitigation: the adjacent `http` middleware line does carry the key name for bearer calls and the username for sessions.
  - [medium] **Audit is written before validation and before the insert, with the name interpolated raw.** At web/app.py:1868 the name and scope list are formatted into the log line before `create()` can reject them, so every 422 (unknown scope, past expiry) is recorded as "issue api key", and a DB failure leaves a success-looking record with no failure marker. Because the name is not escaped, a newline forges log entries: verified `name="a\n[2026-01-01 00:00:00] [system] [api-keys] forged"` produced a second line that `/api/v1/logs` parses as its own `[ts] [user] [source]` record (web/app.py:3277-3281). A NUL character is also accepted and stored.
  - [medium] **A database error mid-create returns 500 and leaks SQL text to lower-privileged log readers.** Nothing wraps `ApiKeyStore.create` (web/app.py:1871-1883), so `SQLAlchemyError` becomes a bare 500 (verified); the audit middleware then logs `EXCEPTION: IntegrityError: … [SQL: INSERT INTO api_credentials …] [parameters: {'id': …, 'digest': …}]` (web/app.py:1266), and `GET /api/v1/logs` returns it unfiltered to a `viewer` (verified 200 and `api_credentials` present) despite its "redacted activity logs" summary (web/app.py:3269). The secret itself is not in the log, but statement/parameter text is.
  - [low] **Minting `admin:*` is permitted to any caller that happens to hold today's nine REST names.** Verified: a key issued with the nine `ENDPOINT_PERMISSIONS` plus `post:/api/v1/admin/keys` successfully minted a child scoped `admin:*` (201), because `expand_scopes("admin:*")` equals exactly those nine names (teledrive/api_keys.py:60). The child then auto-inherits any endpoint later added to `ENDPOINT_PERMISSIONS` (read at request time via `expand_scopes`, teledrive/api_keys.py:65-74), i.e. the child can become more powerful than the parent without any new grant. The same retroactive-widening applies to legacy groups in `LEGACY_SCOPE_EXPANSION` (teledrive/api_keys.py:49-61).
  - [low] **Scopes that grant nothing are accepted as if they were permissions.** Eight legacy names expand to the empty set (`jobs:*`, `accounts:*`, `settings:*`, `keys:manage`, teledrive/api_keys.py:56-59) yet pass `_check_scopes` (teledrive/api_keys.py:104-108) and trivially pass delegation because `frozenset() - limit` is empty. Verified: `scopes: ["keys:manage"]` returns 201, and the resulting key is then 403 on **every** route including this one. The 201 body gives no indication the scopes are inert, which invites support tickets and false confidence.
  - [low] **Input hygiene gaps on `name` and bounds.** Control characters/newlines/NUL are accepted and persisted (verified), names are not unique, `expires_at: true` and numeric strings are coerced by Pydantic lax mode rather than rejected, duplicate scopes are silently collapsed, and the `max_length=20` on `scopes` counts duplicates rather than distinct permissions. The 201 body also omits `expires_at` (verified keys: `id`, `token`, `prefix`, `scopes`) and carries no `Location` header, so a client cannot confirm the expiry it just set.
  - [low] **Unverified:** two concurrent `create` calls with the same name insert independently (distinct random ids/digests, no unique name) — I did not exercise real concurrency, so I cannot confirm or rule out lock contention or duplicate-loss under MySQL. Likewise, MySQL `VARCHAR(120)` truncation/rejection behaviour for 120 astral-plane characters was not tested (SQLite accepts it).
  - [nit] The OpenAPI tag still advertises "Root-admin API key creation, rotation and revocation" (web/app.py:1235) although a non-root bearer key holding this one route permission can mint keys; and the `x-teledrive-csrf` requirement for programmatic bearer callers is undocumented in the endpoint summary (web/app.py:1859).
  - [nit] Error shapes are inconsistent: Pydantic 422s return `detail: [{...}]`, store 422s return `detail: "Unknown or empty permission scope"` (web/app.py:1880) — the same status with two schemas.
  - **Verified as correct (no finding):** operator and viewer sessions are denied (web/app.py:524-525, tests/web/test_auth_rbac.py:372); `admin:*` does not unlock this route; the plaintext token never appears in logs, the list endpoint, or error text; `Cache-Control: no-store` is set; the UI renders the name via `x-text` (web/static/api-management.html:218), so no stored XSS from an HTML/script-laden name; a missing CSRF header or foreign `Origin` is rejected even for bearer callers.
- **Tests that should exist:**
  - `test_issued_key_expiry_cannot_exceed_the_issuing_key` — mint a key with `expires_at = now+60` and only `post:/api/v1/admin/keys`; assert POSTing a child with `expires_at=None` or `now+9y` returns 403/422 and that no row is written. Currently passes the wrong way: both return 201.
  - `test_revoking_a_parent_key_revokes_the_family` — revoke the short-lived parent, then assert the child minted from it gets 403 on this endpoint (today it mints a grandchild with 201).
  - `test_issuance_audit_names_the_actor_and_the_new_key_id` — assert the `api-keys` log entry contains the caller's username/key name and the returned `id`/`prefix`, and does not say `user=system`.
  - `test_issuance_log_is_written_only_on_success` — POST an unknown scope and an expired `expires_at`; assert 422 and that no "issue api key" entry was appended to `LOG_BUFFER`.
  - `test_key_name_cannot_forge_audit_lines` — POST `name="a\n[2026-01-01 00:00:00] [system] [api-keys] forged"`; assert 422, or that `GET /api/v1/logs` still yields exactly one entry for the request and none with `source="api-keys"` and a fabricated timestamp. Today it returns 201 and the forged line parses (verified).
  - `test_create_database_error_returns_502_or_500_without_sql_and_no_secret` — monkeypatch `ApiKeyStore.create` to raise `IntegrityError`; assert the response is 500/503 with a generic body, that `api_credentials` SQL text is absent from `LOG_BUFFER`, and that a `viewer` session cannot read it from `/api/v1/logs`.
  - `test_scope_that_grants_nothing_is_rejected` — POST `{"scopes": ["keys:manage"]}`; assert 422 with a message naming the inert scope. Today 201 (verified).
  - `test_admin_wildcard_cannot_be_minted_by_a_non_session_caller` — a key holding the nine REST names plus `post:/api/v1/admin/keys` must not be able to mint `admin:*` (today 201, verified), or the wildcard must be frozen to the parent's concrete expansion.
  - `test_key_name_rejects_control_characters_and_strips_before_storing` — `"a\x00b"`, `"a\nb"`, `"  padded  "`; assert 422 for control chars and that the stored name equals the stripped input.
  - `test_create_response_reports_expires_at_and_sets_no_store` — assert `expires_at` echoes the request and `Cache-Control: no-store` is present on the 201.
  - `test_duplicate_names_are_allowed_but_logged_with_ids` — two keys named "backup"; assert both list entries are distinguishable by `id` and that each issuance log line carries its `id`.
- **Verdict:** The authorization story is sound — role gate, per-route permission, delegation subset, CSRF and secret handling all hold under probe — but the endpoint lets a mint-capable key create permanent, revocable-only-by-them descendants, and its audit trail neither names the actor nor the created credential while accepting log-forging names; fix those before calling key issuance production-grade.

## rotate_api_key — POST /api/v1/admin/keys/{identifier}/rotate

- **Handler:** web/app.py:1905 (decorator at web/app.py:1904); store logic teledrive/api_keys.py:217
- **Auth model:** `Depends(require_auth)` (web/app.py:570). Two principals reach it:
  - **Bearer API key** (`Authorization: Bearer td_live_…`, web/app.py:575). The key must hold exactly the canonical permission `post:/api/v1/admin/keys/{identifier}/rotate` as resolved from the live route table by `permission_registry().permission_for()` (web/app.py:577-578, web/permissions.py:300). It is then checked by `ApiKeyStore.authorize()` (teledrive/api_keys.py:147-164), and the key's *effective* set is recorded on `request.state.api_key_scopes` (web/app.py:588,597) for the delegation ceiling.
  - **Session cookie** user: role policy + per-user permission gate (`_enforce_role_policy`, `_enforce_user_permission`, web/app.py:607-612). For sessions `api_key_scopes` is absent, so `_delegation_limit()` returns `None` = unrestricted (web/app.py:1837-1840).
  - Second gate for both principals: `_same_origin()` (web/app.py:300) requires header `x-teledrive-csrf: 1`; if an `Origin` header is present it must equal `Host`. Missing header ⇒ 403.
  - Third gate, bearer only: `_require_within_delegation()` (web/app.py:1843-1856) — the target key's effective scopes must be a subset of the caller's (web/app.py:1911-1913).
- **Inputs:** exactly one, the path parameter `identifier: str` (web/app.py:1905). No request body is declared or read. Validation: **none** — no length bound, no charset check, no UUID/hex format check. It is used three ways: (a) as the delegation lookup key in `scopes_for_identifier()`, which matches `id == identifier OR prefix == identifier` (teledrive/api_keys.py:199-207); (b) as the audit-log field (web/app.py:1914); (c) as an equality predicate against `api_credentials.id` inside `rotate()` (teledrive/api_keys.py:221). `rotate()` also accepts `now` (test-only injection, teledrive/api_keys.py:217-218), never supplied by the route.
- **Side effects:** single transaction opened implicitly on the request's connection (web/app.py:1907):
  1. `UPDATE api_credentials SET revoked=1 WHERE id=:identifier AND revoked=0` (teledrive/api_keys.py:231-233); `rowcount != 1` ⇒ `rollback()` + `ValueError` (teledrive/api_keys.py:234-236).
  2. `INSERT` a new row with a fresh `secrets.token_hex(16)` id, fresh `td_live_` + `token_urlsafe(32)` secret, `prefix=token[:16]`, `scopes` copied **verbatim** from the old row, `name` copied, `created_at=now` (**reset**), `expires_at` copied (teledrive/api_keys.py:237-241).
  3. One `commit()` at teledrive/api_keys.py:242; the connection is closed in `finally` (web/app.py:1922-1923), which rolls back anything uncommitted.
  - Logs: one `_log("rotate api key: id={identifier}", "api-keys")` (web/app.py:1914), emitted after the delegation gate but *before* the store attempt, tagged `user=system` (the default at web/app.py:233-235). Separately `_audit_log_middleware` logs `POST <full path>` twice (web/app.py:1253-1272). The secret is never logged.
  - Response: `{"id","token","prefix","scopes"}` (web/app.py:1921). `Cache-Control: no-store` is applied globally to `/api/*` (web/app.py:1329-1330). Verified.
- **Failure modes:**
  - No/invalid credentials ⇒ 401 (web/app.py:614-618).
  - Key lacks the route permission, or key revoked/expired/wrong digest ⇒ 403 "API key is invalid or lacks this endpoint's permission" (web/app.py:599-604).
  - Missing `x-teledrive-csrf` or cross-origin ⇒ 403 (web/app.py:300-310).
  - Target scopes ⊄ caller scopes ⇒ 403 "An API key can only delegate permissions it already holds" (web/app.py:1853-1856) + `auth` log line.
  - Target absent **or revoked** ⇒ `FileNotFoundError` ⇒ 404 (web/app.py:1917-1918, teledrive/api_keys.py:223-224).
  - Target expired ⇒ `ValueError` ⇒ **409** "Cannot rotate expired key" (web/app.py:1919-1920, teledrive/api_keys.py:225-226).
  - Concurrent rotate lost the race ⇒ `ValueError` ⇒ **409** "Concurrent key revocation" (web/app.py:1919-1920, teledrive/api_keys.py:234-236).
  - `INSERT` failure (e.g. digest collision) ⇒ `IntegrityError` escapes both `except` arms ⇒ unhandled 500; rollback happens only via `conn.close()`.
- **Findings:**
  - [high] **`admin:*` keys cannot call this route at all — the preset is dead.** `LEGACY_SCOPE_EXPANSION["admin:*"]` expands to the nine curated `rest:*` names only (teledrive/api_keys.py:60), and `expand_scopes()` never adds canonical route names (teledrive/api_keys.py:65-74). `require_auth` demands `post:/api/v1/admin/keys/{identifier}/rotate` (web/app.py:577-578), which is not in that set, so an `admin:*` key is rejected at auth with 403 before the delegation check even runs. Confirmed by probe: a key minted with `["admin:*"]` rotating **itself** returns 403 "API key is invalid or lacks this endpoint's permission". `admin:*` is still offered in the UI scope list (web/static/app.js:127) and is the natural "full access" choice, so operators can mint keys that are unable to rotate anything. Same class of defect for `keys:manage`, which expands to the empty tuple (teledrive/api_keys.py:59) and therefore grants nothing.
  - [medium] **Existence oracle via 403/404/409.** `scopes_for_identifier()` deliberately does not filter `revoked` or `expires_at` (teledrive/api_keys.py:199-207), so the delegation gate runs on dead keys' scopes *before* the store discovers they are unusable. A caller holding only the rotate permission (and therefore unable to list keys) can distinguish: unknown id ⇒ 404; revoked privileged key ⇒ 403; expired privileged key ⇒ 403; live privileged key ⇒ 403; expired key within own ceiling ⇒ 409 vs unknown ⇒ 404. All five confirmed by probe. The gate should look up the target once, reject dead targets identically, and only then compare scopes.
  - [medium] **`identifier` accepts a prefix for the check but not for the action.** `scopes_for_identifier()` matches `id == identifier OR prefix == identifier` (teledrive/api_keys.py:203-204) while `rotate()` matches `id == identifier` only (teledrive/api_keys.py:221). Confirmed by probe: rotating a *permitted* target by its `prefix` performs the delegation check successfully and then returns 404 "API key not found or revoked", while the same call with `id` returns 200. The 404 is misleading (the key exists and the caller was authorised moments earlier), and it makes the prefix a second existence oracle: any 16-char string matching a high-privilege prefix returns 403, otherwise 404.
  - [medium] **Prefix lookup is ambiguous and unindexed.** `prefix` has no unique constraint (teledrive/api_keys.py:24) and `scopes_for_identifier()` uses `.first()` with no `ORDER BY` (teledrive/api_keys.py:201-204). If two keys ever shared a prefix (16 chars, but only 8 random chars because of the constant `td_live_` head, teledrive/api_keys.py:129,238) the delegation decision would be taken against an arbitrary row. Not exploitable *today* only because `rotate()` is id-only, so the mismatched case always ends in 404 — but the invariant is unenforced. The `revoke` handler (web/app.py:1891) has the same shape.
  - [medium] **Audit trail cannot link the new key to the old one.** Rotation revokes the old id and inserts an unrelated id with the same name; there is no `rotated_from`/`rotated_at` column (schema teledrive/api_keys.py:20-31) and the only log line names the *old* identifier (web/app.py:1914). Post-incident, "which token replaced this one, and when" is unanswerable from the database. The line is also written before the store call, so a rotation that then fails with 404/409 still produces a "rotate api key" entry (verified for both: the `api-keys` buffer held the line after each failure).
  - [low] **Caller-supplied `identifier` is written verbatim to durable logs.** `_audit_log_middleware` logs the full request path (web/app.py:1257, 1260), so `POST /api/v1/admin/keys/td_live_XXXXXXXX/rotate` lands in `LOG_BUFFER`, the rotating file handler and the `/api/logs` websocket stream. Confirmed by probe (the buffer contained a `td_live_…` path fragment). A 404 on a mistyped/pasted **full token** would therefore persist the secret in clear text. The `_log` argument at web/app.py:1914 has the same issue. The middleware should redact anything matching the token shape.
  - [low] **409 is overloaded.** "Cannot rotate expired key" and "Concurrent key revocation" both map to 409 (web/app.py:1919-1920). The concurrency message also names an implementation detail and suggests a permanent failure, when a client retry would succeed.
  - [low] **Atomicity relies on connection close, not on an explicit rollback.** The `INSERT` (teledrive/api_keys.py:237-241) is outside any `try` that rolls back; only the `rowcount != 1` branch rolls back explicitly (teledrive/api_keys.py:234-236). Verified by probe (monkeypatched `insert` to raise): the exception propagates and the old key remains **valid**, because web/app.py:1922-1923 closes the connection and SQLAlchemy rolls back the pending `UPDATE`. The property holds, but it is incidental to the handler's `finally`, not guaranteed by `rotate()`. Any future caller that reuses the connection (or commits in a `finally`) would commit the revoke without the new key — a self-inflicted lockout.
  - [low] **`ApiKeyStore.__init__` runs `ensure_schema()` and commits the connection on every construction** (teledrive/api_keys.py:94-96; `release_setup_snapshot` calls `connection.commit()`, teledrive/db.py:302-319). The handler constructs the store twice (web/app.py:1911, 1916). Today the second construction happens before any write, so nothing is committed early, but this is a latent hazard for any future edit that constructs a store mid-transaction, and it costs two full schema probes per request.
  - [nit] `created_at` is reset to `now` while `expires_at` is preserved (teledrive/api_keys.py:239-240), so a rotated key can appear "created seconds ago" yet expire hours later. `last_used_at` is reset, which is correct but means rotation silently clears usage evidence.
  - [nit] No bound on `identifier` length or format; a 5 KB value is accepted and reaches SQL (probe: 404). A cheap `^[0-9a-f]{32}$` check (or a documented prefix form) would make the contract explicit.
  - **Verified sound (no finding):** the delegation ceiling itself holds for id-based rotation. A key holding `post:/api/v1/admin/keys/{identifier}/rotate` + `objects:read` gets 403 against a live `admin:*` target and cannot obtain the new secret; `expand_scopes()` is applied to both sides (teledrive/api_keys.py:65-74, web/app.py:1849-1850), and the new key's scopes are copied from the *validated* old row rather than from the request, so there is no TOCTOU path to widen authority. The old token stops working immediately (verified: 403 after rotation) and the secret appears only in the response, never in the list endpoint or logs (`no-store` present).
  - **Verified sound (no finding):** the revoke+insert pair is genuinely one transaction; a forced `INSERT` failure leaves the old key usable and creates no orphan row (probe: exactly one row, `revoked=0`).
  - **Verified sound (no finding):** concurrent double-rotate has exactly one winner. Two threads rotating the same id produced `('ok', …)` and `ValueError('Concurrent key revocation')`; the table ends with one active row and one revoked row. No caller receives a secret whose key was then revoked.
- **Tests that should exist:**
  - `test_rotation_delegation_uses_expanded_scopes_for_legacy_target` — target minted with `["admin:*"]`, caller with `["post:/api/v1/admin/keys/{identifier}/rotate","objects:read"]`; assert 403 **and** that the caller's token still works and no new active row exists.
  - `test_rotation_by_prefix_matches_rotation_by_id` — mint a key, rotate it by `prefix`; assert 200 with the same scopes as rotating by `id` (today: 404). This pins the accepted-identifier contract.
  - `test_rotation_of_unknown_revoked_and_expired_targets_are_indistinguishable` — for a caller *without* `get:/api/v1/admin/keys`, assert all three return the same status and the same `detail` (today: 404/403/403, and 409 for an expired target within the caller's ceiling). This is the regression test the existence oracle needs.
  - `test_admin_star_key_can_rotate_a_key` — mint with `["admin:*"]`, rotate another key; assert 200 (today: 403 at auth). This is the test that would have caught the dead-preset bug.
  - `test_rotation_is_atomic_when_insert_fails` — monkeypatch `teledrive.api_keys.insert` to raise, call `ApiKeyStore.rotate`, assert the exception propagates, the old token still authorises, and exactly one row exists for that id with `revoked=False`.
  - `test_concurrent_rotation_yields_exactly_one_live_secret` — two threads on the same id; assert exactly one `IssuedKey`, the other raises, and `authorize()` is true for exactly one of the two returned tokens.
  - `test_rotate_response_is_no_store_and_secret_is_never_logged` — assert `Cache-Control: no-store`, the token is absent from `web.app.LOG_BUFFER`, absent from the `GET /api/v1/admin/keys` body, and that the `api-keys` log line contains the old id but not the token.
  - `test_rotation_records_a_link_to_the_replaced_key` — once `rotated_from` exists, assert the new row points at the old id and that the audit line is emitted only after the commit.
- **Verdict:** The delegation ceiling holds for the id path and the revoke/create pair is atomic, but the endpoint ships three real defects — the `admin:*` preset cannot reach it, dead keys are an existence oracle, and prefixes pass the authorisation check only to 404 — plus an unlinkable audit trail.

## reveal_s3_credential_secret — POST /api/v1/admin/s3-credentials/{identifier}/reveal

> The route in the review brief does not exist: there is **no** `POST …/{identifier}/reveal`, and `POST` to the real path returns 405. The implementation is `GET /api/v1/admin/s3/credentials/{identifier}/secret` with legacy alias `GET /api/v1/admin/s3-credentials/{identifier}/secret`; both decorators share one handler. Findings below are against that real surface.

- **Handler:** web/app.py:5060 (decorators web/app.py:5055 and 5058; store logic teledrive/s3/credentials.py:259-286)
- **Auth model:**
  - **Session cookie principal:** must have role `admin`. `/api/v1/admin/s3/credentials` and `/api/v1/admin/s3-credentials` are in `_ADMIN_ONLY_PREFIXES` (web/permissions.py:79-80), so `is_admin_only()` is true for GET as well (web/permissions.py:110-121); `_required_roles` therefore returns `_ROLE_ADMIN` (web/app.py:524-525) and `_enforce_role_policy` rejects `viewer` and `operator` with 403 before the handler (web/app.py:531-536). Verified: both roles get 403 "Insufficient permissions for this action".
  - **Bearer API-key principal:** no role policy applies — `require_auth`'s key branch (web/app.py:587-616) passes iff the key is active and holds `get:/api/v1/admin/s3/credentials/{identifier}/secret` (or the alias's own `get:/api/v1/admin/s3-credentials/{identifier}/secret`). `ApiKeyStore.authorize` checks revoked/expired and scope expansion (teledrive/api_keys.py:184-200 current tree). Verified: a key minted with exactly that one scope reveals any credential (200), and is 403 on the list endpoint.
  - **Delegation ceiling:** none applies to *reading* a secret. `_require_within_delegation` / `_require_within_lifetime` (web/app.py:1846-1900) are used only by key issue/rotate/revoke. There is no comparison between the caller's scopes and the target credential's S3 permissions.
  - **CSRF / same-origin:** **not enforced.** Every mutating credential route calls `_same_origin(request)` (issue web/app.py:5038, update 5085, revoke 5112) but this handler takes no `Request` and never calls it (web/app.py:5060-5075). Verified: the reveal succeeds with no `x-teledrive-csrf` header and no `Origin` (200). Cross-site *reads* are still blocked because the app registers no CORS middleware (no `CORSMiddleware`/`add_middleware` anywhere in `web/`) and the session cookie is `SameSite=lax` (web/app.py:1621-1622), so a third-party page cannot read the body; an `<img>`/subresource request also omits the Lax cookie.
  - **Host gate:** trusted-host middleware applies app-wide (web/app.py:1262-1269).
- **Inputs:**
  - `identifier: str` path parameter, no `Path(...)` constraint, no length bound, no charset check (web/app.py:5060). It is matched against **either** the credential's UUID `id` **or** its `access_key` (`WHERE id = :x OR access_key = :x`, teledrive/s3/credentials.py:269-270), so an access key (which is not secret and appears in SigV4 headers and logs) can be exchanged for its secret. A 5,000-character value is accepted and reaches SQL (verified 422 "Unknown credential", no length error).
  - No body, no query parameters.
- **Side effects:**
  - Pure read: one `SELECT` against `storage_s3_credentials`, no write, no `commit()` (teledrive/s3/credentials.py:265-270). The connection is opened per request and closed in `finally` (web/app.py:5062, 5074-5075).
  - `S3CredentialStore.__init__` runs `ensure_schema()` on the request connection (teledrive/s3/credentials.py:175-176), so every reveal re-probes the schema.
  - Audit: `_log(f"s3 credential secret revealed: id={identifier} access={revealed['access_key']}", "security")` (web/app.py:5071-5072), written **before** the secret is returned (5073). It carries no secret, but it also carries **no actor**: `_log`'s default `user="system"` is used (web/app.py:233), so the security record reads `[system] [security]`. The only actor identity is in the adjacent framework line `GET <path> from <ip>` (`_audit_log_middleware`, web/app.py:1271-1289 via `_extract_user`).
  - Durability: that audit line lands in `LOG_BUFFER`, an in-memory `deque(maxlen=1500)` (web/app.py:172, 237), plus the rotating file handler when startup installed one (web/app.py:1169-1171). There is no database audit table; a restart or 1,500 subsequent log lines erase the record.
  - Response: `{"id", "access_key", "secret_key", "permissions"}` (teledrive/s3/credentials.py:285-286). `Cache-Control: no-store` is set for all `/api/` responses (web/app.py:1344-1347). Verified: the secret appears in the body only — not in any response header and not in `LOG_BUFFER`; `_log` formats only `id` and `access_key`, so the file handler receives the same secret-free string.
- **Failure modes:**
  - 401 — no session cookie / no bearer (web/app.py:632-636).
  - 403 — key missing this route's permission, invalid, revoked or expired key (web/app.py:617-622); session role not `admin` (web/app.py:531-536).
  - 422 — any `ValueError` from the store, re-emitted verbatim (web/app.py:5069-5070): unknown identifier → `"Unknown credential"` (teledrive/s3/credentials.py:271-272); revoked → `"Revoked credentials have no active secret"` (273-274); expired → `"Expired credentials have no active secret"` (278-279); undecryptable ciphertext → `"Credential secret cannot be decrypted (master key changed?)"` (280-284).
  - 503 — invalid/missing master key *value* (`RuntimeError` from `load_master_key`) with the raw message in the body (web/app.py:5067-5068; teledrive/s3/credentials.py:156-159): `"Set a valid 32-byte Fernet TELEDRIVE_S3_MASTER_KEY"` (verified).
  - 500 — **unhandled** when `TELEDRIVE_S3_MASTER_KEY_FILE` points at a missing file: `os.open` raises `FileNotFoundError` (teledrive/s3/credentials.py:149-153), which neither `except RuntimeError` nor `except ValueError` catches (web/app.py:5067-5070). Verified bare `Internal Server Error`, and `_audit_log_middleware` writes `EXCEPTION: FileNotFoundError: [Errno 2] No such file or directory: '/tmp/…/missing-master.key'` into `LOG_BUFFER` (web/app.py:1284), which a `viewer` reads back through `GET /api/v1/logs` (verified 200 with the path in `entries`) despite that endpoint being advertised as "redacted".
  - 405 — `POST` to the real path (verified).
  - No 429: the reveal route has no throttle. The only throttles are login (`AUTH_FAILURES`, web/app.py:389-409) and the public share endpoints (`_share_rate_limited`). Verified 40 back-to-back reveals all returned 200.
- **Findings:**
  - [high] **One reveal permission discloses every S3 secret, including credentials far more powerful than the caller.** Nothing compares the caller's authority with the target's `permissions`; `reveal()` returns any active row (teledrive/s3/credentials.py:259-286) and the route is gated only on its own permission (web/app.py:5060-5073). Verified: a key minted with only `get:/api/v1/admin/s3/credentials/{identifier}/secret` fetched the secret of a credential holding `s3:PutBucketPolicy` + `s3:DeleteBucket` (200). So the delegation ceiling that stops a key from *minting* broader authority (web/app.py:1861-1874) is bypassed by *reading* a broader credential's secret and then signing with it. Either the reveal permission must be treated as equivalent to all S3 authority (and documented/confirmed as such), or the target's permission set must be constrained to the caller's.
  - [medium] **A missing master-key file is a 500 and leaks its filesystem path to any viewer.** `load_master_key()` only converts `Fernet()` failures into `RuntimeError` (teledrive/s3/credentials.py:156-159); an unreadable/missing key file raises `OSError` out of the handler (verified 500). The audit middleware then logs the exception message including the absolute path (web/app.py:1284), and `GET /api/v1/logs` serves `LOG_BUFFER` unfiltered to a `viewer` (web/app.py:3309-3312; viewer access asserted by tests/web/test_auth_rbac.py:377-383). Verified: viewer response contained `/tmp/opencode/missing-master.key`. This is also an availability defect: a misconfigured deployment answers every reveal with an unhandled exception instead of the intended 503.
  - [medium] **The security audit record has no actor.** `_log(..., "security")` uses the default `user="system"` (web/app.py:233, 5071), so the record that matters for a secret disclosure cannot say *who* disclosed it. Verified log line: `[system] [security] s3 credential secret revealed: id=… access=TD…`. The actor survives only in the separate `http` line, which is a generic request log and can be trimmed independently (`LOG_BUFFER` is one 1,500-entry ring; `GET /api/v1/logs?limit=N` slices it).
  - [medium] **The reveal audit is not durable and is readable by principals without reveal authority.** Secrets-disclosure records exist only in `LOG_BUFFER` (maxlen 1,500) and the optional file log, with no DB audit row (web/app.py:172, 233-258; no audit table anywhere). Meanwhile `GET /api/v1/logs` is a read route granted to `viewer` and returns the buffer unfiltered (web/app.py:3309-3312), so every lower-privileged user can watch *which* credentials are being revealed and when (`id` + `access_key` are in the line), even though the secret itself is not. Verified viewer 200 while the viewer is 403 on the reveal itself.
  - [medium] **"admin only" is inaccurate: any bearer key holding the route permission (or `admin:*` in the current tree) can reveal.** The decorator summary claims "admin only, audit-logged" (web/app.py:5057) and the project TODO repeats "admin-only" (TODO.md:363), but the key branch of `require_auth` deliberately skips the role gate (web/app.py:587-616), and the `admin:*` wildcard now expands to the live route table (teledrive/api_keys.py:98-107 current tree). Verified: both a one-scope key and an `admin:*` key get 200. This is arguably the intended per-route permission model, but the contract text is wrong, and it means "reveal" is a delegable capability that survives admin-session revocation.
  - [low] **A secret-disclosing operation is modelled as GET and therefore skips the CSRF fence.** `_same_origin` is not called (web/app.py:5060-5075), unlike every write on the same resource (5038, 5085, 5112). Verified 200 with no `x-teledrive-csrf`. Cross-site exfiltration was **not** demonstrated: there is no CORS middleware, the session cookie is `SameSite=lax` (web/app.py:1621-1622), and the response is `no-store` (1347), so a cross-origin page cannot read the JSON. Residual risk is audit/log pollution from prefetchers, link scanners and top-level navigations, plus any future CORS or `SameSite=None` change turning this into a one-line secret theft.
  - [low] **Unknown, revoked and expired identifiers are trivially distinguishable,** and all three return 422 rather than 404/410: `"Unknown credential"` vs `"Revoked credentials have no active secret"` vs `"Expired credentials have no active secret"` (teledrive/s3/credentials.py:271-279, web/app.py:5069-5070). Verified all three. An identifier is a UUIDv4 or a 96-bit access key, so enumeration is impractical — but a caller without list permission still gets a state oracle for a value it already holds, and 422 is the wrong status for "no such secret".
  - [low] **No rate limit or budget on secret disclosure.** Verified 40 sequential reveals all 200. With a stolen admin session or a leaked reveal-scoped key, all credentials can be dumped and each dump pushes an audit line into a 1,500-entry buffer; nothing throttles or alerts.
  - [low] **Failed reveals are not recorded as security events.** `_log(... "security")` is only reached after `reveal()` succeeds (web/app.py:5064-5072), so unknown/revoked/expired/decrypt-failure probes produce only the generic `http` status line. A burst of 404-equivalent probes by a reveal-capable key is not distinguishable from ordinary traffic in the security stream.
  - [low] **Master-key error text discloses configuration details.** The 503 body echoes `Set a valid 32-byte Fernet TELEDRIVE_S3_MASTER_KEY` (teledrive/s3/credentials.py:159) and the decrypt path answers `(master key changed?)` (280-284). No key material or path is exposed in the body (verified), but both confirm the deployment's key-management state to any admin caller and belong in the server log rather than the response.
  - [low] **The reveal audit contract is unenforced, and other callers ignore it.** `reveal()`'s docstring says "every reveal must be audit-logged by the caller" (teledrive/s3/credentials.py:262-264) but nothing enforces it; `_signing_credential` calls `store.reveal()` with no audit line at all (web/s3_governance_api.py:338-339), so the stated invariant ("every reveal is audited") is already false in the same codebase. Verified by inspection.
  - [nit] `identifier` has no format/length bound (a 5,000-character value reaches SQL), and the canonical/alias paths are two distinct permissions for one operation (`get:/api/v1/admin/s3/credentials/{identifier}/secret` vs `get:/api/v1/admin/s3-credentials/{identifier}/secret`, web/permissions.py:173, 175) — verified: a key granted the canonical permission is 403 on the alias and vice versa. Operators must grant "reveal" twice if they want the documented permanent alias to work for keys.
  - **Verified sound (no finding):** the session role gate is correct (`viewer`/`operator` 403, verified); the plaintext secret appears only in the JSON body and never in response headers, `LOG_BUFFER` or error text (verified); `Cache-Control: no-store` is present (verified); revoked and expired credentials are refused by the store (teledrive/s3/credentials.py:273-279) and an expired credential is refused over HTTP (probe), not just at store level; a changed master key yields a generic 422 rather than ciphertext; the response leaks no other row fields (name, tags, timestamps are not returned).
- **Tests that should exist:**
  - `test_reveal_permission_cannot_disclose_a_broader_credential` — mint a key with only the reveal scope, create a credential holding `s3:PutBucketPolicy`, assert the reveal is 403 (today 200). **This is the mandatory regression test** for the escalation path.
  - `test_reveal_denied_for_viewer_and_operator_sessions` — `viewer` and `operator` GET the reveal URL with a valid session; assert 403, no `secret_key` in the body, and a `denied:` auth log entry.
  - `test_reveal_audit_names_the_actor_and_not_the_secret` — reveal as user `alice` and as a named API key; assert the `security` log line contains `alice` / `api-key:<name>`, the credential `id`, and does **not** contain `[system]` or any substring of `secret_key`.
  - `test_reveal_missing_master_key_file_fails_closed_without_leaking_path` — point `TELEDRIVE_S3_MASTER_KEY_FILE` at a nonexistent path; assert 503 (not 500), the body does not contain the path, `LOG_BUFFER` does not contain the path, and a `viewer` cannot read the path from `/api/v1/logs`. Today: 500 and the path is in the viewer-readable buffer.
  - `test_reveal_unknown_revoked_and_expired_are_indistinguishable` — all three must return the same status and the same `detail` (today 422 with three distinct messages), and none may contain `secret_key`.
  - `test_reveal_expired_credential_over_http_is_refused` — expire a credential directly in SQL, then GET the route; assert the same refusal as revoked (the existing coverage is store-level only, tests/s3/test_s3_acl.py:385-400).
  - `test_reveal_requires_csrf_or_is_not_a_get` — pin the intended contract: either the header is required (route becomes POST, matching the documented `…/reveal`) or the GET exemption is documented and asserted together with the absence of CORS and `no-store`.
  - `test_reveal_failed_attempt_is_audited_as_a_security_event` — probe an unknown id and a revoked id; assert a `security`-source entry records each failure with the actor and outcome.
  - `test_reveal_is_rate_limited_per_principal` — 20+ reveals in a burst; assert 429 after a documented threshold and that the throttle key is the user/key id, not the client IP.
  - `test_reveal_by_access_key_requires_the_reveal_permission_and_is_audited` — call with the `access_key` instead of `id`; assert 200 for a permitted caller, 403 for a key without the scope, and that the log records which identifier form was used.
  - `test_reveal_secret_never_reaches_logs_or_cache` — assert `Cache-Control: no-store`, the secret is absent from `LOG_BUFFER` and from the file log, and it is not present in any response header.
- **Verdict:** Authorization by role is correct and the secret never escapes into logs, headers or caches — but a reveal-scoped key can extract the secret of any more-privileged S3 credential (verified), the audit entry names no actor and is neither durable nor viewer-safe, and a missing master-key file turns into an unhandled 500 that writes the key path into a viewer-readable log.

Accepted set is `("revoked","deleted","queued")` (gc_collect.py:66); anything else is rejected at gc_collect.py:206-207 and surfaces as 422 via web/app.py:4541-4542. `revoked` is also the WebUI default (`gcScope: 'revoked'`, web/static/app.js:28).
  - `dry_run: bool = True` — the safe mode is the default; execution requires the caller to set `false` explicitly (web/app.py:4543).
  - `min_age_seconds: int = 86400`, `ge=3600`, `le=90*86400` (web/app.py:1385), re-checked against `MIN_AGE_FLOOR_SECONDS=3600` in gc_collect.py:208-209. **Ignored entirely for `scope="queued"`**, which uses the stored `grace_seconds` instead (gc_collect.py:219-224).
  - `limit: int = 50`, `ge=1`, `le=1000` (web/app.py:1386), re-checked at gc_collect.py:210-211 and applied at gc_collect.py:224, 266.
  - `confirm: str | None = None` (web/app.py:1387) — compared with exact `!=` against `"DELETE-RETAINED"` (web/app.py:4546). Case-sensitive, whole-string, so `"delete-retained"`, `""`, `null` and any partial value all fail closed. Checked *before* the enable check and before any deletion, but *after* candidate enumeration (read-only).
- **Side effects:** for each candidate, in this order (gc_collect.py:317-341 → 344-428):
  1. re-verify status/head/alias/object-lock/send-intent (gc_collect.py:348-377);
  2. `transport.delete(ref)` for every primary chunk, one await per chunk (gc_collect.py:388-397), which calls `client.delete_messages(chat_id,[message_id])` (teledrive/storage/telethon_adapter.py:79-85 via teledrive/storage/user_mode.py:814-833) — **irreversible**;
  3. `DELETE storage_chunks` for the deleted ordinals, `DELETE storage_replica_chunks` (gc_collect.py:399-403) — replica messages are *not* deleted;
  4. `INSERT storage_gc_collected` (object, bucket, key, chunk_count, bytes, scope, `deleted_refs` JSON, `collected_ns`) (gc_collect.py:407-411);
  5. if no chunks remain: `INSERT storage_removed_versions` + `UPDATE storage_objects SET status='gc-collected'` + pending-tag cleanup (gc_collect.py:412-426);
  6. a single `self.db.commit()` per object (gc_collect.py:427) — so the SQL side of one object is atomic, but the Telegram deletes are outside any transaction.
  - For `scope="queued"` the queue row is deleted after a `collected`/`skipped` outcome (gc_collect.py:326-332), which is a second commit.
  - Audit: two `_log` lines with `scope`, counts and username (web/app.py:4554-4556, 4561-4564), plus the state-changing HTTP audit line from `_audit_log_middleware` (web/app.py:1272-1280). `LOG_BUFFER` is a 1500-entry in-memory deque (web/app.py:172) and the file handler is optional (web/app.py:255-256), so logs are not the durable record. The durable record is `storage_gc_collected`, written *after* the Telegram deletes and inside the object transaction.
- **Failure modes:**
  - missing session/API key → 401 (web/app.py:632-636); API key without the permission → 403 (web/app.py:619-622); operator session → 403 (web/app.py:531-536).
  - missing `x-teledrive-csrf` / cross-origin → 403 (web/app.py:301-312).
  - invalid `scope` / `min_age_seconds` / `limit` → 422 from `candidates()` (web/app.py:4541-4542); malformed body → 422 from FastAPI.
  - `dry_run=false` without `confirm="DELETE-RETAINED"` → 422 (web/app.py:4546-4548), no deletion.
  - GC disabled and `dry_run=false` → 409 (web/app.py:4549-4551); `collect()` repeats the check and raises `PermissionError` (gc_collect.py:312-313).
  - no authorized Telethon user session → 503 (web/app.py:4552 → 1476-1489).
  - per-object failure (Telegram error, inaccessible account, SQL error) → swallowed per object and reported in `failed[]` with `str(exc)[:200]`, HTTP 200 (gc_collect.py:322-325, web/app.py:4565). **A failed Telegram delete is *not* marked collected**: the status/chunk/journal writes only run after the whole delete loop returns. But the converse is broken — see `[critical]` below: the SQL writes can fail *after* the deletes succeeded.
  - A non-per-object exception (e.g. `asyncio.CancelledError`, which is `BaseException` and not caught by `except Exception`) propagates, `conn.close()` rolls back (web/app.py:4567-4568), and the Telegram deletes already issued are lost with no journal entry.
- **Findings:**
  - [critical] **Every collection of a version-revoked object destroys the media and then fails deterministically, leaving the object "ready" with dangling chunk rows.** `_collect_object` inserts `storage_removed_versions` unconditionally when the last chunk is removed (gc_collect.py:415-416), but `delete_version` has *already* inserted that row at revocation time (teledrive/storage/catalog.py:751). The second insert raises `UNIQUE constraint failed: storage_removed_versions.object_id`, the exception is caught as a per-object `failed` (gc_collect.py:322-325), `commit()` is never reached, and `conn.close()` rolls the chunk/journal/status writes back — **after** `client.delete_messages` already ran. `scope` defaults to `"revoked"` (web/app.py:1383), i.e. the endpoint's default action is this path. Verified by probe (single object, single call, no concurrency): `scope=revoked via delete_version in_removed=1 cands=1 telegram_deleted=[9001] report={'collected':0,'failed':1} status=ready chunks=1 journal=0`. The object stays `ready`, so it is enumerated again on every retry (infinite destructive-failure loop) and any read now 404s mid-object. `scope="queued"` hits the same wall for version-delete objects (verified: `telegram_deleted=[9001] collected=0 failed=1 queue_rows_left=1`), and so does `scope="deleted"` on a bucket using Suspended versioning, where the delete retires the target through the same `removed_versions` insert (catalog.py:633-650). This contradicts docs/S3_SPECS.md:108.
  - [critical] **No post-deletion safety window: `min_age_seconds` is measured from the last chunk write, not from the logical delete, and the owner's `grace_seconds` is ignored by the scopes this endpoint uses.** `candidates()` filters on `objects.updated_at < now - min_age` (gc_collect.py:259), and `updated_at` is only advanced by chunk append/finish (teledrive/storage/manifest.py:452,476); `delete_version` deliberately writes `updated_at=objects.c.updated_at` (a no-op, catalog.py:713-718), versioned `delete_marker` only writes a new marker row and re-points the head (catalog.py:659-698), and `remove_current` only deletes the head row (catalog.py:1300-1320) — none of them advances the target's `updated_at` on a well-formed row. `gc_state.grace_seconds` is read only for `scope="queued"` (gc_collect.py:219). Verified by probe: an object uploaded 48 h ago and revoked *seconds* ago is a candidate at `min_age_seconds=3600` while the stored grace is 86400. So a version-revoked object can be physically destroyed one hour (or, for an old upload, immediately) after revocation, with no recovery window — a revoked version is unrecoverable once its media is gone.
  - [high] **No lease or row fence: two concurrent collect calls delete the same Telegram messages twice, and the loser rolls back its bookkeeping after the media is already gone.** `_collect_object` uses plain `SELECT`s (gc_collect.py:348-377) with no `FOR UPDATE`, and the object has no claim column. Verified with two connections that both enumerated candidates first (exactly what web/app.py:4538 does): both issued `delete_messages` for message 9001; the second failed (`database is locked` / `UNIQUE constraint failed: storage_gc_collected`), and the final state was `status=ready, chunks=1, journal=0` — i.e. media destroyed, catalog unchanged. There is no idempotency key on `storage_gc_collected` beyond its PK, which is what converts the duplicate run into a rollback.
  - [high] **The "re-verify immediately before deletion" reads from the snapshot pinned by the candidate preview, so it is not a current read.** The endpoint builds `RetainedMediaGC` and calls `candidates()` (web/app.py:4536-4540) and then `collect()` on the *same* connection, so one transaction spans the entire run; every later `SELECT` sees the snapshot taken at preview time on snapshot-isolating backends (MySQL REPEATABLE READ, SQLite WAL). The codebase already knows this hazard and works around it elsewhere with a locking current-read (`with_for_update` at catalog.py:726-730, and the `release_setup_snapshot` comment at teledrive/db.py:302-319). A head published, an alias created or a legal hold applied after the preview can therefore be invisible to the fence, and the media is deleted from under it. PostgreSQL's READ COMMITTED (fresh snapshot per statement) masks this; the documented MySQL target does not.
  - [high] **Destruction is not recoverable after a crash, cancellation or shutdown mid-object, and there is no write-ahead intent.** Telegram deletes precede the only `commit()` (gc_collect.py:388-427), and `_collect_object` is not resumable: chunks deleted before a failure are not recorded anywhere (contrast the send path, which journals `mtproto_send_intents` first, gc_collect.py:370-377). An operator later sees `failed[]` with no indication of *which* messages are already gone, and the object remains restorable/shareable while its bytes are missing.
  - [high] **A scoped API key can execute the most destructive operation in the product with no role and no human gate.** web/app.py:587-622 returns before `_enforce_role_policy`, so the admin-only classification (web/permissions.py:81) does not apply to keys. Combined with the static confirm token, a key holding `post:/api/v1/admin/storage/gc/collect` — or the pair `put:…/gc` + `post:…/gc/collect`, which lets it enable GC itself — deletes Telegram media with two scripted requests. Mitigation to state plainly: minting such a key still requires admin (web/app.py:1897-1907).
  - [medium] **The confirm token is a constant, not bound to the previewed set.** `"DELETE-RETAINED"` is compared literally (web/app.py:4546) and the WebUI re-enumerates on execute (web/static/app.js:50-56) instead of sending the previewed ids; the server honours `scope`/`limit`, not what the operator saw. A preview of 5 objects can therefore delete a different 50. The word is also trivially producible by any client, so it is an accident brake, not authorization.
  - [medium] **The durable journal cannot attribute the actor.** `storage_gc_collected` (gc_collect.py:54-64) has no `collected_by`, request id or reason column; the only attribution is in the log lines (web/app.py:4554-4556), which live in a bounded in-memory deque (web/app.py:172) and an optional rotating file. After rotation the deletion of a given message cannot be attributed to a principal.
  - [medium] **The kill switch does not stop a run in progress.** `enabled` is read once (web/app.py:4549, gc_collect.py:312) and never re-checked per object, so an admin who disables GC during a 1000-object run does not stop it.
  - [medium] **Replica media is orphaned, not deleted.** gc_collect.py:402-403 deletes `storage_replica_chunks` rows without ever calling `transport.delete` for the replica coordinates (available from `replica_refs`, teledrive/storage/manifest.py:593-600). The replica messages stay in Telegram forever with no row pointing at them, and are unreclaimable by any later GC.
  - [medium] **The preview ignores object lock and legal hold, so the dry run lies about what will be deleted.** `candidates()` (gc_collect.py:254-266) and `metrics.reclaimable` (gc_collect.py:161-183) have no retention/legal-hold predicate; only execution checks them (gc_collect.py:360-369). Verified by probe: an object with `retention_until_ns` in the future and `legal_hold=1` is still returned as a preview candidate, then silently `skipped` at execution. For an irreversible action the preview should be the authoritative list.
  - [medium] **MPU-abort queue entries can never be collected, so the queued backlog is permanently wrong.** Abort enqueues staged *part* object ids (web/s3.py:2065-2077) whose objects are `status="pending"` (teledrive/s3/multipart.py:650-653), but `candidates(scope="queued")` requires `status="ready"` and a published version (gc_collect.py:230-238). Those messages are never deleted by any path and `metrics["queued"]` (gc_collect.py:187) counts them forever. This endpoint's `queued` scope is the only drain.
  - [medium] **No rollback after a per-object failure.** gc_collect.py:322-325 catches the exception and continues on a connection whose transaction may be aborted; on PostgreSQL every following object then fails at its first `SELECT` (so its media survives, but the run reports a wall of failures), and on SQLite the loop keeps going and commits the rest. A single `db.connection.rollback()` in the handler would make the behaviour backend-independent.
  - [low] **HTTP 200 with `failed[]` is indistinguishable from success for scripts.** web/app.py:4565 returns 200 even when every candidate failed (or when the SQL side of every object rolled back after the media was destroyed). A non-empty `failed` should surface as a 5xx/207, and a run that deleted media without recording it must never look like a clean 200.
  - [low] **Raw SQL/driver error strings are returned to the API caller** via `report["failed"][].reason` (gc_collect.py:323-324, web/app.py:4565), e.g. the full `UNIQUE constraint failed …` statement. Admin-only, but it leaks schema detail into the response body (and into any client-side log).
  - [low] **Unbounded synchronous work.** `limit` up to 1000 objects × every chunk, all inside one request (web/app.py:1386, 4557), with no job id, progress endpoint or resume token; a proxy timeout or restart mid-run leaves the last object in the state described above.
  - [nit] `scope` should be `Literal["revoked","deleted","queued"]` with a `max_length`, so the contract is visible in OpenAPI instead of a 422 from deep inside `candidates()`.
  - [nit] `_same_origin` is skipped when `Origin` is absent (web/app.py:303-305); for bearer callers it is only a header-presence check.
  - **Verified sound (no finding):** the confirm comparison is exact and case-sensitive, and it is evaluated before `storage_transport` and before any delete (web/app.py:4546 vs 4552-4560); `""`, `null`, `"delete-retained"` and prefixes cannot pass.
  - **Verified sound (no finding):** the enable toggle is *independently* required — `dry_run` preview works while disabled (read-only), execution is refused with 409 both in the handler (web/app.py:4549-4551) and again inside `collect()` (gc_collect.py:312-313).
  - **Verified sound (no finding):** the head and dedup-alias fences are correct on the object being collected (`heads.object_id`, `object_aliases.source_object_id`, gc_collect.py:353-359, 261-263), and every dedup/copy path records an alias pointing at the resolved base (teledrive/storage/engine.py:170-186, teledrive/storage/copy.py:86-88), so a shared payload is protected.
  - **Verified sound (no finding):** share links cannot pin doomed media — they store only `(bucket, object_key)` (teledrive/db.py:128-141) and resolve the live head at download time (web/app.py:5446), while a GC candidate is by definition not a head.
  - **Verified sound (no finding):** a failed Telegram delete does **not** mark the row collected; `status='gc-collected'`, chunk deletion and the journal insert all follow the delete loop (gc_collect.py:399-427).
  - *(unverified)* Whether real Telethon `delete_messages` raises on an already-deleted message id; if it does not (the usual behaviour), the retry loop in `[critical]` burns API calls forever without making progress, and the object can never leave `ready`.
- **Tests that should exist:**
  - `test_collect_revoked_scope_does_not_collide_with_removed_versions` — publish at `now-48h`, `delete_version`, enable GC, `collect(scope="revoked")`; assert `collected==1`, `failed==[]`, `storage_chunks==0`, one `storage_gc_collected` row and `status='gc-collected'`. **Fails today** (IntegrityError) and is the mandatory regression for the `[critical]` finding.

This pins the "never destroy before the record exists" invariant.
  - `test_two_concurrent_collects_delete_each_message_exactly_once` — two connections that both enumerate candidates, then collect; assert `transport.delete` sees each message once, exactly one `collected` and one `skipped`, one journal row, and the object ends `gc-collected`.

## telegram session request/verify code — POST /api/v1/admin/storage/telegram/session/{request,verify}-code

> Note: the routes are registered hyphenated, as `/api/v1/admin/storage/telegram-session/request-code` and `.../verify-code`; there is no `/telegram/session/...` path. Review covers the pair as one login unit.

- **Handler:** web/app.py:2741 (`request_telegram_session_code`) and web/app.py:2838 (`verify_telegram_session_code`); shared helpers `_telegram_error_response` at :2650, `_consume_pending_session_token` at :2638.
- **Auth model:** principal is any authenticated session cookie (`require_auth`, web/app.py:582) **or** any bearer `td_live_*` API key holding the route's permission (web/app.py:587-622). Gates applied: `_same_origin` (:2745, :2842 — requires the literal `x-teledrive-csrf: 1` header and rejects a present `Origin` that differs from `Host`), outer role gate `_required_roles` (:510-528), inner permission gate `_enforce_user_permission` (:539-554). For POST, `_required_roles` returns `_ROLE_WRITE = {admin, operator}` because `telegram-session` is absent from `_ADMIN_ONLY_PREFIXES` (web/permissions.py:76-82), so **operator is sufficient**; viewer gets 403 (probe). API keys bypass roles entirely (`return` at :616 before `_enforce_role_policy`), so a key minted with `post:/api/v1/admin/storage/telegram-session/{request,verify}-code` can bind an account with no human role. Both handlers are reachable only after authentication; neither is in the public prefix list (permissions.py:234-241).
- **Inputs:**
  - `request-code` (`TelegramSessionRequestCode`, web/app.py:2630-2635): `api_id: int` (no upper bound; only `<= 0` rejected at :2747), `api_hash: str` (non-empty, no max length), `phone: str` (non-empty, no format/length bound; passed verbatim to Telethon at :2783 and stored), `channel: str | None` (unvalidated; empty → server picks the active or first channel, :2753-2771), `strategy: str | None` (unvalidated, defaults to `round_robin`, :2820, :2937). Missing fields → FastAPI 422; `api_id<=0` or empty hash/phone → 400 (:2747-2748).
  - `verify-code` (`TelegramSessionVerifyCode`, web/app.py:2830-2833): `token: str` (no max length; only a lookup key), `code: str` (only checked for emptiness at :2871; arbitrary length), `password: str | None` (optional 2FA password, used once at :2897, never persisted).
  - Body size is bounded only globally by `MAX_REQUEST_BYTES` in `security_middleware` (:1299-1315); no per-field bounds. Schema columns are `String(64)`/`String(128)` (teledrive/db.py:90-105) but SQLite does not enforce them.
- **Side effects:**
  - `request-code` opens a disposable Telethon `StringSession()`, calls `send_code_request(phone)` and **saves that unauthorized MTProto session string** plus `phone_code_hash`, `api_id`, `api_hash`, `phone`, `channel`, `strategy` into `telegram_session_pending` (:2810-2821; schema teledrive/db.py:90-105). The row is keyed only by a random `token = secrets.token_urlsafe(16)` (:2750) — **no user id, session id or principal column exists**. The token (128 bits) is returned to the caller along with the phone number and `expires_in: 300` (:2826-2827).
  - Pruning only happens as a side effect of the *next* `request-code`: `DELETE ... WHERE created_at < now-300` (:2810-2812). There is no scheduled purge and no delete on failed verify.
  - `verify-code` loads the row by token alone (:2848-2852), checks a soft 300 s age (:2862), then reuses the stored session string for `sign_in(phone, code=..., phone_code_hash=...)`; on `SessionPasswordNeededError` it makes a second `sign_in(password=...)` call (:2892-2897). On success it deletes the pending row (:2933), deletes any `telegram_sessions` row for the same `account` and inserts the new session string (:2943-2955), optionally deactivates **every** channel and activates/creates the supplied one (:2960-2990), writes `AUTH_DIR.parent/sessions/<account>.session` with `_secure_write` (:2993-2999), and triggers a runtime reload (:3002).
- **Failure modes:** 422 pydantic (missing/invalid JSON); 400 missing api_id/api_hash/phone (:2747-2748) or empty `code` (:2871); 403 missing CSRF header / cross-origin (:300-312) or insufficient role/permission; 401 unauthenticated; 429 Telegram `FloodWaitError` on send or sign-in, with the wait persisted and returned (:2794-2802, :2908-2916); 404 unknown token (:2855-2857); 410 expired (>300 s, :2862-2864) or pre-fix row without a session string (:2865-2870); 410 `PhoneCodeExpiredError`, which consumes the token (:2917-2926); 400 for every other Telethon error, including `PhoneCodeInvalidError` and `PasswordHashInvalidError`, via `_telegram_error_response` (:2927-2931) — **the pending row survives these**, by explicit design (:2928-2930). Unexpected DB errors after sign-in produce 500 after the token was already consumed.
- **Findings:**
  - [high] **Binding a Telegram account — a storage-wide, data-plane operation — is authorized for `operator`, not `admin`.** `telegram-session` is not in `_ADMIN_ONLY_PREFIXES` (web/permissions.py:76-82), so `_required_roles` returns `{admin, operator}` (web/app.py:526-528). Probe: operator POSTed `request-code` and got 200 with a token; admin's roles are never consulted anywhere in either handler. An operator can therefore attach their own Telegram account, make it the backend for all future uploads, and (via the bundled channel activation at :2960-2990) deactivate every other channel — i.e. redirect/own the storage backend. The same reach is available to an operator-scoped API key because keys skip role enforcement (web/app.py:616); this pair is exactly the kind of credential-minting surface that should be admin-only, like `/admin/keys` and `/admin/s3/credentials`.
  - [high] **`verify-code` has no attempt cap, no delay and no lockout, and a wrong code (or wrong 2FA password) deliberately leaves the pending row usable — so the 5-digit code and the account's 2FA password can be brute-forced for the full 300 s window.** The only terminal paths are success (:2933), age >300 s (:2862), and `PhoneCodeExpiredError` (:2917-2926); `PhoneCodeInvalidError` and `PasswordHashInvalidError` fall into the generic 400 that explicitly does not consume (:2927-2931). There is no counter column, no per-token attempt tracking, no `FloodWait` gate before `sign_in`, and no shared failure bucket like `AUTH_FAILURES` (:264) for this flow. Probe with a fake Telethon client: 10 consecutive wrong codes all returned 400, the pending row still existed after each, and the 11th (correct) attempt returned 200 — 10 sign-in attempts in seconds with no server-side friction. The only remaining bound is Telegram's own per-`phone_code_hash` attempt limit (unverified how strictly it applies to the separate `sign_in(password=...)` call at :2897, which is a different surface and may be throttled far less aggressively). Anyone holding the token (see next finding) can grind 2FA passwords this way.
  - [medium] **The pending login is global, not keyed to the requesting principal: any authenticated user who learns a token can complete another user's Telegram login.** The table has no owner column (teledrive/db.py:90-105) and the lookup is `WHERE token = :token` only (:2848-2852). Probe: operator called `request-code`, then a *different* principal (admin) called `verify-code` with that token and received 200, producing a saved session under the operator-initiated login. The 128-bit token is the sole binding, is returned in a JSON body (:2826) and held in browser state (`tgSessionToken`, web/static/app.js:606), so impact is bounded by token confidentiality — but there is no defense in depth, no revocation of someone else's pending login, and no audit trail naming the requester beyond a first-8-chars log line (:2843).
  - [medium] **`request-code` is unthrottled and never consults the FloodWait state it records, so it can spam login codes to arbitrary phone numbers and prolong its own lockout.** `_flood_wait_status()` (:2708) is read only by the GET status endpoint (:2735); neither POST checks it before `send_code_request` (:2744-2783). Any operator can loop this with an arbitrary `phone` (no ownership check possible for Telegram, but also no rate limit, no per-principal budget) — Telegram abuse/harassment plus an IP-wide `FloodWait` that blocks legitimate re-login. Each hit also inserts an unbounded `flood_waits` row (:2689-2692) with no dedup or retention.
  - [medium] **Abandoned pending logins keep a plaintext phone number, `api_hash`, and a live unauthorized MTProto auth key in the database indefinitely.** Rows are only pruned when a *later* `request-code` happens to run (:2810-2812); there is no scheduled job and no delete on failed verify. Probe: after 10 failed verifies the row (and its `session_string`) was still present, and grep confirms no other `telegram_session_pending` cleanup exists. The stored session string is the auth key `phone_code_hash` is bound to (:2785-2791, :2882-2893) — combined with a code intercepted or phished within five minutes and DB read access, it is directly usable to finish the login; at minimum it is long-lived secret material outside the credential store.
  - [medium] **Raw exception text is returned to the caller and written to the shared log with only URL/query secret scrubbing, so a phone number or other PII in an exception message is disclosed.** `_telegram_error_response` builds the response from `_scrub_text(str(exc))` (:2676-2678), and `_scrub_text` only masks `scheme://user:pass@` and query-string secrets (:295-297) — no phone/OTP redaction. Probe with a synthetic `RuntimeError("proxy rejected request for +15551230003")` produced `400 {"detail":"proxy rejected request for +15551230003 [RuntimeError]"}`. The same string is logged (:2677) into the buffer served by `GET /api/v1/logs` (web/app.py:1271-1289), whose permission is a read route, so viewers can read it too. Real Telethon errors for this flow carry generic text (`PhoneCodeInvalidError`, `PhoneNumberInvalidError`), so real-world phone leakage is *unverified* — but the scrubbing contract is wrong for a login flow that handles phone numbers and OTPs.
  - [medium] **Expiry check and row consumption are not atomic, so two concurrent `verify-code` calls for one token both proceed.** The row is read in one connection (:2845-2854, closed), the age is checked, and only much later (after a multi-second Telethon round-trip) is the row deleted in a *separate* connection (:2933 → :2638-2647). Two simultaneous requests therefore both pass existence/expiry, both call `sign_in` with the same session/hash, and both can reach the delete-then-insert into `telegram_sessions` (:2943-2955, no unique constraint on `account` in teledrive/db.py:57-76), producing duplicate session rows and a second sign-in that should never have been sent. *Unverified by probe* (would require real Telegram concurrency); the read/delete separation is verified in code.
  - [low] **The pending token is consumed before the session is persisted, so a DB failure after a successful Telegram sign-in loses the login.** `_consume_pending_session_token` runs at :2933, then the `telegram_sessions` write is a separate connection (:2939-2958). If that write fails, the caller gets 500 with the token already gone and must redo the SMS/code (and the code hash is burned).
  - [low] **Session-file write failures are swallowed while the API reports success.** :2993-2999 wraps `_secure_write` in `except Exception: pass` and still returns `ok: true` with a `session_file` path that may not exist. The DB row is the runtime source of truth, so this is not data loss, but it silently breaks any file-based consumer.
  - [low] **Login silently rewrites storage-wide channel configuration from unvalidated caller input.** `channel`/`strategy` come straight from the request body (:2753, :2820) and a successful verify runs `UPDATE telegram_channels SET is_active = 0` for all rows, then activates/creates the named channel and writes the strategy (:2960-2990). A login should not be able to silently deactivate every channel, and `strategy` should be a `Literal` so an invalid value cannot be persisted for the runtime to consume.
  - [low] **`verify-code` discloses a server filesystem path** (`session_file`, :3007), and 404/410/400 distinguish token states (unknown vs expired vs pre-fix vs wrong code) — a minor oracle on an unguessable token.
  - [low] **Telegram-controlled `account` (username) is interpolated into the session-file path** at :2994 (`f"{sessions_dir}/{account}.session"`). Telegram usernames are restricted to `[A-Za-z0-9_]`, and `_secure_write` uses `O_NOFOLLOW` plus mode 0600 (:284-292), so traversal is not currently reachable — but there is no local validation, so a future account source (display name, config) would make this a path-injection sink.
  - [nit] The token prefix (first 8 chars) is logged at :2843 and :2860 — unnecessary for debugging and reduces the token's effective secrecy slightly.
  - [nit] `password` is accepted and silently ignored when Telegram does not ask for 2FA (it is only read inside the `SessionPasswordNeededError` branch, :2894-2897); the client cannot tell whether it was used.
  - [nit] `strategy`/`channel` have no `max_length` while the DB columns are `String(32)`/`String(255)`; and `api_id` should probably be bounded to a sane positive range.
  - [nit] *(adjacent route)* `GET /api/v1/admin/storage/telegram-session` returns the phone **unmasked** (:2621) to any viewer, while `GET .../telegram-sessions` masks it with `_mask_phone` (:2533) — inconsistent handling of the same PII that this pair stores.
  - **Verified sound (no finding):** the session string is never returned to the browser — the success body is only `{ok, account, user_id, session_file}` (:3003-3008), and the GET status route omits it (:2611-2624). Probe confirmed the fake session string did not appear in any response.
  - **Verified sound (no finding):** success clears the pending row (:2933; probe: row count 0), and `PhoneCodeExpiredError` clears it too (:2917-2920).   - **Verified sound (no finding):** the written session file is mode `0600` in a `0700` directory (probe: `0o600`), opened with `O_NOFOLLOW` (:284-292).
  - **Verified sound (no finding):** viewer role is blocked on both POSTs (403, probe), and CSRF header absence is blocked (403) before any Telegram call (:2745, :2842).
  - **Verified sound (no finding):** a wrong code does not consume the token (:2928-2931) — intentional, and necessary for a retry; the defect is the missing cap around it, not the retry itself.
  - *(unverified)* Whether real Telegram throttles the second `sign_in(password=...)` call (2FA) as tightly as code attempts; if it does not, the `[high]` brute-force finding extends to account 2FA passwords, not just the 5-digit code.
  - *(unverified)* Whether an operator can reach this pair through any additional legacy `/api/...` alias not enumerated here; only the two registered `/api/v1/...` paths were exercised.

## put_object_content — PUT /api/v1/buckets/{bucket}/content

- **Handler:** `web/app.py:5317` (route declared `web/app.py:5315-5322`). All behaviour lives in the shared core `_stream_object_upload` at `web/app.py:5255-5312`, which is also the body of the session-cookie twin `admin_upload_object` (`web/app.py:3560-3569`). Engine path: `TelegramObjectStorage.put_file` (`teledrive/storage/engine.py:105-133`) → either `_dedup_lookup` (`engine.py:135-198`) or `_put_file_inner` (`engine.py:312-445`) → `ManifestStore.begin/append/finish` (`teledrive/storage/manifest.py:212-233`, `404-454`, `456-491`) → `BucketCatalog.publish` (`teledrive/storage/catalog.py:1016-1117`).
- **Auth model:** exactly one principal and no second gate.
  - **Principal:** a bearer API key (`Authorization: Bearer td_live_…`). The route's only dependency is `require_api_scope("rest:objects:put")` (`app.py:5320` → `app.py:1517-1530`), which validates the token with `ApiKeyStore.authorize` (`teledrive/api_keys.py:184-201`). Missing credentials → 401 with `WWW-Authenticate: Bearer` (`app.py:1519-1522`); invalid/expired/revoked or insufficient scope → a single generic 403 (`app.py:1528-1529`).
  - **Role policy:** not applied and not applicable. This route never calls `require_auth` (`app.py:582-636`), so `_enforce_role_policy` (`app.py:531-536`) and `_enforce_user_permission` (`app.py:539-554`) never run; a key's authority is exactly its expanded scopes (`teledrive/api_keys.py:97-111`). A browser session cookie alone gets 401, so no session role can reach it.
  - **CSRF / same-origin:** not applied. `_same_origin` is only called by the twin (`app.py:3568`); for the bearer route it is unnecessary (no ambient credential) and a cross-origin browser `fetch` with an `Authorization` header would need a preflight that no CORS policy for `/api/` answers. Not a finding.
  - **Can an API key reach it:** yes. `rest:objects:put` is the curated name (`web/permissions.py:137`, `teledrive/api_keys.py:34-44`); the legacy group `objects:write` (`api_keys.py:82`) and `admin:*` (`api_keys.py:97-111`) also grant it.
  - **Read-only scope cannot write:** verified. `authorize` requires the required name to be an exact member of the expanded set (`api_keys.py:195`), `objects:read` expands only to list/list-versions/get/head (`api_keys.py:80-81`), and there is no `rest:objects:*` wildcard in the accepted scopes (`api_keys.py:92-94`). Pinned by `tests/web/test_api_keys.py:106`.
  - **No per-bucket authorization exists:** the scope is global. `bucket` is only checked for membership (`app.py:5270`), so a key holding only `rest:objects:put` may overwrite any object in any bucket, including buckets it cannot list or read, and may create new keys on its own. This is the model, but it makes every put-scoped key a write capability over the whole tenant (see the bucket-policy finding).
- **Inputs:**
  - `bucket` — path string, no `pattern`/`max_length` on the route (`app.py:5318`) or on the shared core; the sole validation is `bucket not in catalog.list_buckets()` → 404 (`app.py:5270-5271`). Legal names are `[a-z0-9](?:[a-z0-9.-]{1,61}[a-z0-9])` with extra rules (`catalog.py:100`, `140-145`), so an illegal name is a 404 rather than a 422 and is only reachable through the middleware's body-buffering branch (see nit).
  - `key` — required query parameter, `min_length=1, max_length=1024` (`app.py:5318`). Pydantic bounds **characters**; the store requires **1..1024 UTF-8 bytes** (`catalog.py:149`). `manifest.begin` does not validate the key at all (`manifest.py:214`), so a 600-character non-ASCII key is accepted here and rejected only at publish time.
  - `generation` — optional `int`, `ge=0` (`app.py:5319`). `0` means create-if-absent, `n>0` is optimistic concurrency (`catalog.py:1022-1023`). Checked before any body is read (`app.py:5272-5280`) and re-checked atomically in the publish CAS (`catalog.py:1040-1100`).
  - `Authorization` — bearer token, ≤200 chars, must start `td_live_` (`api_keys.py:186-188`).
  - `Content-Type` — must be `application/octet-stream` before any `;` parameters, else 415 (`app.py:5258-5259`). Checked after auth, before bucket existence.
  - `Content-Length` — **never read on this path.** The only `content-length` checks are in `security_middleware` (`app.py:1303-1309`), which explicitly excludes this route via the `binary_upload` regex (`app.py:1294-1299`). A lying, absent, zero or negative value has no effect on the cap; with `Transfer-Encoding: chunked` the request works normally.
  - `Content-Encoding`, `aws-chunked`, `Content-MD5`, `x-amz-checksum-*`, `x-amz-decoded-content-length` — not referenced anywhere in `web/app.py` (grep: zero hits). The body is stored byte-for-byte, whatever the framing, with no metadata recording the encoding.
  - `Host` — must be in `ALLOWED_HOSTS`, else 400 (`app.py:1262-1268`).
  - Body bound — `1..REST_MAX_UPLOAD_BYTES` (default 2 GiB, `app.py:85`, `teledrive/settings.py:135-137`), enforced **while streaming** by a running counter (`app.py:5288-5291`); `0` disables the surface with 503 (`app.py:5261-5262`). There is no lower bound, so an empty body is a valid 0-byte object.
- **Side effects (exact order):**
  1. `_secure_mkdir(STORAGE_SCRATCH_DIR)` → mkdir/chmod 0700 (`app.py:5263-5264`, `268-281`); chmod failure is swallowed.
  2. `db_connect()` (`app.py:5265`) — one DB connection is held for the entire transfer, through body read and Telegram upload, and closed only in `finally` (`app.py:5312`).
  3. Reads: `catalog.list_buckets()` (`5270`), optional head read for `generation` (`5274`), `storage_transport` (`5281`), `transport.verify_target()` (`5283`, a no-op — `teledrive/storage/user_mode.py:659-660`).
  4. `tempfile.mkstemp(dir=stage_root, prefix="api-upload-")` → mode 0600 file (`5284`); the body is streamed into it with a byte counter, then `flush()` + `fsync()` (`5287-5294`). This happens **before** any quota check.
  5. Read-only quota evaluation `_enforce_bucket_quota` (`5296` → `4194-4212`): `SELECT` of `bucket_quotas` and of current-head usage.
  6. Engine: for a dedup hit, a full synchronous SHA-256 pass (`engine.py:146-153`), then `INSERT storage_objects(status='ready')` + `INSERT storage_object_aliases` + `commit()` (`engine.py:176-185`) and **no Telegram traffic at all**; for a miss, `INSERT storage_objects(status='pending')` + commit (`manifest.py:220-232`), writer fence row (`324`), chunk files at 0600 (`359-362`), one `transport.upload` per chunk (`374-380`, sequential or `parallel_degree()`-wide) → MTProto send + send-journal `start`/`acknowledged` (`user_mode.py:738`, `777`), one `INSERT storage_chunks` + commit per chunk (`manifest.py:445-454`), best-effort replica send (`engine.py:402-405`), `UPDATE storage_objects SET status='ready', sha256=…` + commit + writer-fence delete (`manifest.py:474-490`), then a synchronous full-file read for the content index (`engine.py:426-432`).
  7. `catalog.publish`: CAS on `storage_object_heads`, `INSERT storage_published_versions`, notification, metadata journal, single commit (`catalog.py:1051-1117`), then `apply_default_lock` in a second transaction (`1070`, `1116`).
  8. `finally`: `staged.unlink(missing_ok=True)` and `conn.close()` (`5309-5312`). No SQL rollback is needed for the staged file, and Telegram messages from a failed upload are deliberately retained as a recovery journal (`engine.py:434-442`).
  9. Nothing is written to any audit table: the object write appears only as the generic HTTP log line (`app.py:1279-1288`) and as a metadata-journal row with `detail={"size": …}` and no actor (`catalog.py:1064-1066`, `1112-1114`).
- **Failure modes:**
  - 400 — `Host` not allow-listed (`app.py:1266-1267`).
  - 401 — no credentials or non-bearer scheme (`app.py:1519-1522`).
  - 403 — unknown/expired/revoked key, or key lacking `rest:objects:put` (`app.py:1528-1529`).
  - 422 — missing/empty `key`, `key` longer than 1024 characters, negative `generation` (FastAPI, `app.py:5318-5319`).
  - 415 — `Content-Type` not `application/octet-stream`, before the body is read (`app.py:5258-5259`).
  - 503 — uploads disabled by policy (`5261-5262`); no authorized Telethon USER session (`app.py:1488-1489`, `storage_transport`).
  - 404 — bucket not in the catalog (`5270-5271`).
  - 409 — stale `generation` before staging, zero Telegram bytes (`5272-5280`); or a publish-time CAS/length failure after the full upload (`5301-5305`).
  - 413 — body exceeded `rest_max_upload_bytes` mid-stream (`5290-5291`); bucket size/object quota exceeded (`4204-4212`), checked after the body is fully staged.
  - 500 — uncaught `ValueError` from `catalog.get` when `generation` is supplied with a key >1024 UTF-8 bytes (`5273-5276` catches only `FileNotFoundError`; `catalog.py:548` → `149-150`); `OSError`/`ENOSPC` while writing the staged file (`5292`); any transport error, including the deliberately ambiguous `RuntimeError("MTProto send outcome uncertain…")` (`user_mode.py:786-794`).
  - Cancellation/client disconnect — `CancelledError`/`ClientDisconnect` propagates out of `request.stream()`, `finally` unlinks the staged file and closes the connection, and no object row exists yet because `manifests.begin` runs only after the body is complete. Conversely, once the body is fully received, a disconnect no longer cancels the upload, so the object can be published while the client sees a broken connection.
  - 201 — `{id, bucket, key, size, sha256, generation}` (`5306-5308`). `sha256` is the digest of the bytes the server **received and staged**, not of the bytes Telegram holds.
- **Findings:**
  - [high] **Bucket policy, ABAC and resource ACLs are not evaluated, so an explicit `Deny` can be bypassed through this endpoint.** `_stream_object_upload` checks only bucket existence and quota (`app.py:5270`, `5296`); it never loads `BucketPolicyStore`, `BucketAbacStore` or ACLs. The S3 data plane evaluates all three immediately before a write (`web/s3.py:2795-2817`: explicit deny → `"Access denied by bucket policy"`, then ABAC at `2810-2812`, then ACL at `2815`). The operator documentation states the opposite invariant — "the owner **and the bucket policy** still apply" and "an explicit Deny always wins" (`docs/UPGRADING.md:107`, `128`). Consequence: a bucket policy such as `Deny s3:PutObject` with `Principal: "*"` on `arn:aws:s3:::b/*` blocks boto3 but not a key holding `rest:objects:put` (or `objects:write`, or `admin:*`), on the same bucket and prefix. Verified by code path (no policy call is reachable from `app.py`); no runtime probe was possible without a shell.
  - [high] **A publish-time failure leaves the uploaded media permanently unreclaimable.** `manifests.finish` commits `status='ready'` and the digest (`manifest.py:474-490`) before `catalog.publish` runs (`app.py:5300-5305`). If publish raises, the handler returns 409, but the object row is already `ready` with all chunks recorded and no head and no `storage_published_versions` row. GC candidates require `exists(published_versions.object_id, objects.id)` (`teledrive/storage/gc_collect.py:281`), so this object is invisible to every scope and its Telegram messages can never be reclaimed. Deterministic trigger, fully static-verified: `PUT` with a key whose UTF-8 length is 1025-4096 bytes (e.g. `"é"*600`, well inside the 1024-**character** bound) → body is uploaded to Telegram, then `catalog.publish` calls `_keyhash(item.key)` (`catalog.py:1026`, `148-151`) → `ValueError` → 409 `"Object key must contain 1..1024 UTF-8 bytes"` with the media orphaned. The same orphan arises from the documented CAS losers (`catalog.py:1059`, `1098-1100`) and from a bucket deleted mid-upload (`1027-1028`). The dedup branch leaks a `ready` alias row the same way (`engine.py:176-185` before `app.py:5300`).
  - [high] **Bucket quota is check-then-write with no reservation, so concurrent uploads exceed it without bound; the check is also wrong for overwrites.** `_enforce_bucket_quota` only `SELECT`s current usage and compares (`app.py:4194-4212`), and is called after staging (`5296`) but before a multi-minute Telegram upload (`5300`); nothing reserves the bytes and no transaction or lock spans the gap. Two simultaneous 2 GiB PUTs into a 3 GiB bucket both pass and both commit. There is also no per-key quota, rate limit or concurrency cap anywhere (grep for `per_key|key_quota|Semaphore` → no matches), so the only bound on a single put-scoped key is the process-wide 2 GiB per request. Separately, usage is `SUM(head.size)` (`app.py:4183-4191`), so replacing an existing key counts the old version as well as the new one (`4204-4207`), rejecting an overwrite that would actually fit — the opposite error, at the quota boundary.
  - [medium] **Nothing verifies the bytes Telegram actually holds before publishing, and `finish` checks only sizes.** `manifest.finish` compares `SUM(chunks.size)` with the declared size (`manifest.py:468-473`) and records the locally computed digest; `transport.upload` records the send-journal ACK without comparing the remote bytes (`user_mode.py:772-779`); `_put_file_inner` never re-downloads a chunk (`engine.py:371-406`). Per-chunk digest verification exists only on the read path (`engine.py:660-671` → `_verified_fetch`), so a truncated, substituted or otherwise corrupt send is published as `201` and fails only on the next GET (or silently serves the replica). The `sha256` in the response is therefore not evidence that the object is readable.
  - [medium] **`key` is validated in characters while the store requires bytes, giving two different errors for one input.** Without `generation`: full upload, then 409 and orphaned media (see `[high]`). With `generation=0`: uncaught `ValueError` from `catalog.get` → **500** before any body is read, because `app.py:5273-5276` catches only `FileNotFoundError`. A single `key.encode("utf-8")` check in the handler would make both a 422 and close the orphan trigger.
  - [medium] **The whole upload path performs blocking disk I/O on the event loop, and reads the staged file up to three extra times.** `sink.write` and `os.fsync` of up to 2 GiB run inline in the coroutine (`app.py:5287-5294`); `_dedup_lookup` does a full synchronous SHA-256 pass (`engine.py:146-153`); `_put_file_inner` reads 64 MiB chunks and writes part files synchronously (`engine.py:347-362`); `index_object_content` reads the file again (`engine.py:426-432`). No `run_in_executor`/`anyio.to_thread` is used on this path, so one large upload stalls every other request in the process, including `/api/health`, for the duration of each blocking call.
  - [medium] **The write is not durably audited with the real actor.** The only attribution is the middleware's `PUT /api/v1/buckets/{bucket}/content -> 201` line with the key name (`app.py:1279-1288` via `_extract_user`, `190-230`), stored in a 1500-entry in-memory deque plus an optional rotating file (`app.py:172`, `255-256`). The durable rows carry no actor: `storage_published_versions` / the metadata journal get `detail={"size": N}` only (`catalog.py:1064-1066`, `1112-1114`), and `storage_objects` has no creator column. Contrast the governance routes, which call `_audit(request, actor, …)` explicitly (`web/s3_governance_api.py:123-126`). After rotation, "who overwrote this key" cannot be answered from SQL or logs, and the log line does not even contain the object key.
  - [medium] **Disk staging precedes any admission control, and a crash leaks the staged file forever.** Up to `rest_max_upload_bytes` is written to `STORAGE_SCRATCH_DIR` before the quota check (`app.py:5284-5296`) with no free-space preflight and no upload concurrency limit, so a put-scoped key can fill the volume with `N × 2 GiB`. `finally` cleans up on every in-process exception (`5309-5311`), but there is no startup sweep for `api-upload-*` (grep: no reference outside the request), so SIGKILL/OOM/power loss leaves the full partial body on disk permanently.
  - [medium] **An unconditional PUT can silently undo a concurrent DELETE, and the conditional variant only discovers the conflict after the whole upload.** With `generation=None`, `publish` inserts a fresh head whenever none exists (`catalog.py:1044-1050`), so a PUT that started before a `DELETE /objects` finishes after it resurrects the key at generation 1 — the delete is not a barrier and there is no `If-Match`/ETag alternative. With `generation` set, the mismatch is detected at `5301-5305`, i.e. after every byte has been sent to Telegram, which is exactly the orphan case above.
  - [medium] **No client-supplied checksum is accepted or verified.** `Content-MD5` and `x-amz-checksum-*` are ignored (no references in `web/app.py`), unlike the S3 surface (`web/s3.py:2830-2833` verifies the upload digest). A client cannot ask the server to reject a corrupted body; it can only compare the returned `sha256` after the object is already published.
  - [low] **`Content-Encoding` and `aws-chunked` are stored verbatim with no metadata.** A `Content-Encoding: gzip` body (or an `x-amz-content-sha256: STREAMING-…` body with AWS chunk framing) becomes a permanently opaque object: the GET side sends `Content-Type: application/octet-stream` and no `Content-Encoding` (`app.py:5380-5385`). Rejecting unknown encodings with 501, or recording them, would prevent silent corruption.
  - [low] **`verify_target` is a no-op that is documented as a pre-body access check.** The comment at `app.py:5282` says "Verify Telegram access BEFORE consuming a potentially large body", but `UnifiedUserTransport.verify_target` only calls `runtime.require()` (`user_mode.py:659-660`), which `storage_transport` already did (`app.py:1484`). The same token is also written in full to the log stream by the audit middleware, which logs `request.url.path` unredacted (web/app.py:1274,1280,1288), and `GET /api/logs` is likewise readable by any viewer (web/app.py:3308-3310); verified: viewer `/api/logs` 200 and the full token present. Both paths survive the viewer's own revocation and give a read-only account the ability to publish data outside the product.
  - [high] **The link is key-scoped and always resolves the live head, so overwriting an object silently changes what an already-delivered URL serves, and deleting then re-uploading the same key resurrects a URL the operator believed dead.** `catalog.get` resolves `heads.object_id` by `(bucket, key_hash)` (teledrive/storage/catalog.py:547-559) and the handler stores only `(bucket, object_key)` (web/app.py:3894-3901). Verified probe: create link → GET returns `version-one`; overwrite same key → same link returns `version-two-SECRET` (200); delete key → 404; re-upload same key → same link returns `version-three` (200). Deleting an object is therefore not a revocation, and a share can never be pinned to the bytes that were reviewed.
  - [medium] **The default link never expires, has unlimited downloads and no password.** `expires_in`, `max_downloads` and `password` are all optional, and `expires_at = now + expires_in if expires_in else None` (web/app.py:3898); verified stored row `(expires_at, max_downloads, password_salt) = (None, None, None)` for a body of `{"key": ...}`. For a surface whose whole job is bounded public exposure, permanent-and-unlimited should be an explicit opt-in (or forced through an admin-only route), not the zero-argument default.
  - [medium] **Revoking a link does not stop an in-flight download.** `admin_revoke_share` deletes the row (web/app.py:3956-3958), but `_stream_share` has already claimed the slot and holds its connection to the running `iter_bytes` generator (web/app.py:5540-5545), which never re-checks `share_links`. Verified probe: pause the stream, `DELETE /api/v1/admin/storage/shares/{token}` → 200, release the stream → the full 65,536-byte body is still delivered with 200; only subsequent requests 404. Also, deletion rather than `revoked=1` makes the schema's `revoked` column and the listing's `"revoked"` status unreachable (teledrive/db.py:141, web/app.py:3926-3927; no `SET revoked` anywhere), and destroys the row that would otherwise be the revocation audit trail.
  - [medium] **An operator — and a single-scope API key — can create public links, and the handler performs no object-level authorization at all.** Role gate is operator-or-admin (web/app.py:506,524-528); verified operator 200. The handler's only checks are bucket membership and `catalog.get` success (web/app.py:3881-3886); bucket policy, ABAC, object ACL grants, storage class/restore state and legal hold are never consulted, so the share capability publishes bytes based solely on route permission. Quota and website publishing are admin-only precisely because they change public exposure (web/permissions.py:83-86); a never-expiring unauthenticated URL belongs to the same class. (Whether an operator can actually be denied a read by an existing bucket policy on other paths is *unverified*; the missing check here is confirmed.)
  - [medium] **The commit-04b6a4c `share_links` cleanup on bucket delete cannot be exercised for any bucket that can hold a share, and the token keeps working after the attempted delete.** `delete_bucket` refuses any bucket with a single `storage_objects` row (teledrive/storage/catalog.py:1329-1342), and object rows are never deleted (`grep delete(objects)` finds no such path), so `DELETE /api/v1/buckets/backup-bucket` returned 409 `"Bucket has object history; safe physical GC required"` while a live share existed, and `GET /share/{token}` was still 200 afterwards. When deletion does run (empty history), the purge is in the same transaction before `commit()` (catalog.py:1406-1425,1431-1434), and `tests/storage/test_storage_catalog.py:145` pins it, so a *successful* delete does kill the URL and a re-created bucket cannot revive it. The guarantee is sound but vacuous end-to-end.
  - [medium] **No durable per-use audit and no actor on the share-specific creation log.** The only record of a download is `download_count`; there is no row with time, IP, actor, object version or bytes served, and successful downloads are not logged at all (web/app.py:5512-5555). Creation logs `user=system` because `_log(...)` defaults to `"system"` (web/app.py:233, 3905-3907) — verified log line `[system] [share] share link created: …` — while the SQL row's `created_by` is never surfaced in the log; revoke is equally unattributed (web/app.py:3964). Attribution only exists by correlating the separate HTTP line, which itself leaks the token.
  - [low] **Password gate is sound cryptographically but weakly bounded operationally.** Per-link 16-byte salt, PBKDF2-SHA256 at 200k iterations (lower than the 260k used for user logins, web/app.py:315 vs 5467), `hmac.compare_digest` (web/app.py:5599), plaintext never stored or logged (`password=yes/no`, web/app.py:3907), and a wrong password does not consume a slot (verified `download_count=0` after a 401). But a 1-character password is accepted (web/app.py:3874-3876), and brute force is limited only by the shared per-IP GET+POST limiter (60/min, web/app.py:5445-5460) — there is no per-token attempt counter, so distribution across IPs is unbounded, and 60/min per IP also throttles legitimate downloads of every link behind one NAT.
  - [low] **No cache directives on the shared bytes.** The streaming response sets only `Content-Length`, `Content-Disposition` and `nosniff` (web/app.py:5549-5555); there is no `Cache-Control: no-store` (or `private`), so browser or intermediary caches may retain a password-gated payload after the link is revoked or expires.
  - [low] **A deleted object or an SSE-C object burns a download slot before the failure is known.** The counter is incremented first (web/app.py:5518-5525) and only then is the head resolved and the engine invoked (web/app.py:5526-5542); the object may already be gone, and `iter_bytes` without `sse_key` raises `SSECError` after 200 headers were sent (engine.py:632-636). Functionally, SSE-C objects can never be shared successfully.
  - [low] **Unvalidated `key` produces a 500 and type confusion.** Over-long keys raise an uncaught `ValueError` (catalog.py:149) instead of 422; `key: ["a"]` becomes the literal string `"['a']"` and yields 404 (web/app.py:3854).
  - [nit] `payload: dict = Body(...)` exposes no request schema in OpenAPI, so bounds are invisible to clients; `max_downloads: 1.9` is silently truncated to 1; `_load_active_share` catches every exception and returns `None`, so a database outage is indistinguishable from an expired link (web/app.py:5506-5507); the claim `UPDATE` does not repeat the expiry predicate (web/app.py:5518-5522) though the preceding `_load_active_share` does (web/app.py:5499-5503), leaving a sub-millisecond TOCTOU; the rate limiter is process-local (web/app.py:5441-5442) and resets on restart (`workers=1` in web/unified.py:75, so not multiplied today).
  - **Verified sound (no finding):** token entropy is 192 bits from `secrets.token_urlsafe` with a PK uniqueness constraint (web/app.py:3889, db.py:130); the revocation regex and public-route regex both require `[A-Za-z0-9_-]{16,64}` (web/app.py:3951, 5494); expiry is checked server-side on every GET and POST via integer comparison `expires_at > int(time.time())` (web/app.py:5499-5503, verified by tests); unknown/expired/exhausted/revoked all collapse to the same 404 page (web/app.py:5492-5509); the download-count decrement is a single conditional `UPDATE … WHERE download_count < max_downloads` with `rowcount == 1` checked, and a verified 8-thread race on `max_downloads=1` produced exactly one 200 and `download_count=1`; token lookup is a PK equality against a 192-bit secret (no practical timing oracle), and the password comparison is timing-safe; plaintext passwords are never persisted or logged.
- **Tests that should exist:**
  - `test_share_tokens_are_not_readable_by_non_admin` — seed a viewer, create a passwordless share as admin, then assert `GET /api/v1/admin/storage/shares` as the viewer is 403 (or omits/redacts `token`) and that no `/api/logs` entry contains the token. **Fails today** on both counts; this is the mandatory regression.
  - `test_share_link_follows_only_the_reviewed_version` — create a share, overwrite the key with different bytes, assert the old token is 404 (or still returns the original object), i.e. the link either pins a version/ETag or is invalidated on head change.
  - `test_delete_then_reupload_does_not_resurrect_a_share` — create share, delete key, re-upload same key, assert 404 and that the share row was invalidated at delete time.
  - `test_default_share_requires_an_explicit_unbounded_opt_in` — `POST {"key": ...}` must 422 (or require `expires_in`), and only an explicit flag may produce `expires_at IS NULL`.
  - `test_revoke_aborts_an_in_flight_download` — pause `iter_bytes`, revoke, resume; assert the response is truncated/aborted and fewer than `size` bytes are delivered, and that `revoked=1` remains queryable.
  - `test_operator_cannot_create_a_permanent_public_link` — operator session: either 403 for the route, or 403 when no expiry is supplied; pin the policy explicitly.
  - `test_create_share_rejects_an_overlong_key_with_422` — 2000-byte key returns 422, never 500; and `key` that is not a string returns 422.
  - `test_bucket_delete_with_a_live_share_removes_the_url` — currently blocked by the 409 history guard; assert the intended contract once deletion is reachable (token 404, `share_links` row gone, re-created bucket does not revive it).
  - `test_share_download_records_a_durable_audit_event` — assert one row per successful download carrying token, object version, IP and timestamp; and that the creation log line carries the actor rather than `system`.

- **Verdict:** Not shippable as a public exposure surface: read-only viewers and anyone with log access can harvest live tokens, an issued URL follows the live head (and revives after delete+re-upload), revocation cannot stop an in-flight stream, and the zero-argument default is a permanent unlimited anonymous URL.

## user management — create / change role / delete / change password

- **Handler:** web/app.py:3403 (`create_user`), :2016 (`change_user_role`), :3436 (`delete_user`), :1983 (`change_user_password`). Route templates take `{user_id}` (int), **not** `{username}` as the brief states; there is also **no** `POST /api/v1/auth/password` route — `grep` finds none and a probe returns 404, so the only password mutation is the admin route `PUT /api/v1/admin/users/{user_id}/password`. All four are in `web/app.py`; no service layer.
- **Auth model:**
  - **Session principal:** the path prefix `/api/v1/admin/users` is in `_ADMIN_ONLY_PREFIXES` (web/permissions.py:76-97), and `is_admin_only()` (web/permissions.py:118-129) therefore makes the outer gate `_ROLE_ADMIN` for every method (web/app.py:510-528). Operator and viewer sessions are refused 403 by `_enforce_role_policy` (web/app.py:531-536); the inner map `_enforce_user_permission` (web/app.py:539-554, web/permissions.py:307-357) is redundant defence in depth. There is no per-object ownership check: any admin can mutate any account, including the bootstrap account.
  - **Bearer API key:** `require_auth` short-circuits the role gate for `Bearer td_live_…` and admits the key iff it holds exactly the route's canonical permission, or `admin:*` expanded over the live route table (web/app.py:587-622; web/permissions.py:307-330). Keys are deliberately not users (web/permissions.py:20-24).
  - **CSRF / same-origin:** every handler calls `_same_origin` (web/app.py:1985, 2018, 3405, 3437) which requires `x-teledrive-csrf: 1` and, when `Origin` is present, an exact `netloc == Host` match (web/app.py:300-312). It also applies to bearer keys. No CORS middleware is installed, so a browser cannot set the custom header cross-origin without a failing preflight; this part is sound.
  - **Bootstrap:** `_create_default_admin` seeds `admin`/`admin` at startup whenever no row named exactly `admin` exists, and leaves an existing row untouched (web/app.py:430-460, especially 444-453).
- **Inputs:**
  - `create_user`: `UserCreateRequest` (web/app.py:3395-3398) — `username: str` (only truthiness checked at 3406, no strip, no length, no charset), `password: str` (only `len >= 8` at 3410), `role: str = "viewer"` (whitelist `admin|operator|viewer` at 3408). Pydantic has no `max_length`, no `extra="forbid"` and no strip; SQLite stores whatever is sent (`String(128)` is not enforced by SQLite, teledrive/db.py:151-162).
  - `change_user_role`: raw `payload: dict`; `role` is `str(...).strip()` and must be exactly one of the three names (web/app.py:2019-2021). Unknown roles are rejected, and the permission map fails closed for an unknown role anyway (web/permissions.py:341-343).
  - `delete_user`: path `user_id: int` only (web/app.py:3436).
  - `change_user_password`: raw `payload: dict`; `password = str(payload.get("password", ""))`, `len >= 8` (web/app.py:1986-1988). No max length, no complexity, no old-password field, no target-role restriction.
  - No handler accepts a username in the path, so there is no path-injection surface; the id is resolved by equality.
- **Side effects:**
  - `create_user`: one `users` row (role as supplied), commit, then a second `SELECT id` in the same connection (web/app.py:3416-3427). Any exception on INSERT is collapsed to 409 “username already exists” (3423-3424). No session is issued and no default password is forced.
  - `change_user_role`: one `UPDATE users.role`, commit (web/app.py:2031-2034). Sessions are **not** deleted, but `_get_current_user` re-reads role from the joined row on every request (web/app.py:477-498), so a demotion is effective immediately on the existing token — verified: operator demoted to viewer, same `Bearer` token then returned `role: viewer` from `/api/auth/me` and 403 on a write (probe P1).
  - `delete_user`: one `DELETE FROM users` (web/app.py:3447-3449). **`user_sessions` rows are not deleted** (no FK/cascade, teledrive/db.py:170-175), and SQLite reuses the highest rowid: a new account created after deleting the highest-id user gets the same `users.id`, so the deleted user's live token then authenticates as the new account. Verified end-to-end: victim (id 6, viewer) deleted, `newadmin` created at id 6, old victim token returned `{id: 6, username: newadmin, role: admin}`, listed API keys 200 and created another admin 201.
  - `change_user_password`: `UPDATE users.password_hash`, then `DELETE FROM user_sessions WHERE user_id = :uid`, commit (web/app.py:1999-2006). Session revocation is correct here (existing test `test_change_password_revokes_sessions`).
  - Audit: `_log` defaults to `user="system"` (web/app.py:233-236) and all four mutation calls omit the actor: web/app.py:2008, 2035, 3430, 3451. Verified lines are `[system] [users] create user: …`, `change role: …`, `change password: user_id=…`, `delete user: …` with no acting admin; the separate HTTP middleware line carries the actor but not the target (web/app.py:1280-1293).
  - Attacker gains: (a) a key with only `post:/api/v1/admin/users` can create an `admin` account and log in with it — full admin (verified); (b) a key with only `put:/api/v1/admin/users/{user_id}/password` can reset the bootstrap/another admin's password and log in; (c) a deleted user who kept a session token inherits the next account created at the reused id; (d) anyone who can reach a renamed deployment's restart gets `admin`/`admin` back.
- **Failure modes:**
  - 401 — no session/key, expired token, or token whose user row was deleted/disabled (web/app.py:482-497, 632-636).
  - 403 — operator/viewer session (role gate 531-536); missing/foreign CSRF header or mismatched Origin (300-312); bearer key lacking the exact route permission (617-622).
  - 400 — blank username/password, role outside the three names, password shorter than 8 (web/app.py:3406-3411, 2019-2021, 1987-1988).
  - 404 — unknown `user_id` in role/password/delete (web/app.py:2028-2029, 1997-1998, 3444-3445). A nonexistent path `/api/v1/auth/password` is 404 (verified).
  - 409 — duplicate username (3423-3424); demoting/deleting the last admin (1451-1461). The 409 is misleading for *any* INSERT failure (length/constraint/disk), which is mapped to “username already exists”.
  - 422 — non-integer `user_id`; missing/typed-wrong `UserCreateRequest` fields. `change_user_role`/`change_user_password` take `dict` and perform no schema validation, so `{"password": 12345678}` is coerced to `"12345678"`; a non-dict body is 422.
  - 500 — uncaught DB errors during the post-INSERT `SELECT` (3425-3427) or in role/password updates; on a backend that enforces `String(128)`, an over-long username is a DataError caught and reported as 409, not 400/422 (unverified: probe was SQLite).
  - 201 — create success; returns `{id, username, role}` with no `Location` and no password-change requirement.
- **Findings:**
  - [critical] **Deleting a user does not delete their sessions, and SQLite rowid reuse lets a revoked token come back as the next account — including an admin.** `delete_user` only deletes the `users` row (web/app.py:3447-3449); `user_sessions` has no foreign key or cascade (teledrive/db.py:170-175); `users.id` is a plain `Integer` primary key, i.e. SQLite `INTEGER PRIMARY KEY` without `AUTOINCREMENT` (teledrive/db.py:151-153), so the next INSERT after deleting the max id reuses it. `_get_current_user` joins solely on `user_sessions.user_id = users.id` (web/app.py:477-481). Verified: delete user id 6 → session row for user_id 6 survives → create `newadmin` → id 6 → the deleted viewer's old token now returns `role: admin`, `GET /api/v1/admin/keys` 200, and `POST /api/v1/admin/users` 201. This turns account deletion into delayed privilege escalation for a hostile ex-user who kept their Bearer token (cookies are harder but the token is returned by `/api/auth/login`, web/app.py:1632). Fix: delete sessions in the same transaction as the user (or add `ON DELETE CASCADE` + `AUTOINCREMENT`/identity), which makes the rowid reuse harmless.
  - [high] **An admin can disable the last *enabled* admin and lock everyone out, because the last-admin guard ignores `enabled` and is not called on the enable/disable path.** `_assert_not_last_admin` counts `users WHERE role='admin'` only (web/app.py:1451-1461) and `update_user` calls it only when `role is not None` (web/app.py:2089-2091); setting `enabled: false` (2110-2118) has no guard. Verified: with `admin` (enabled) and `admin2` (admin, disabled), `PUT /api/v1/admin/users/1 {"enabled": false}` returned 200, the actor's live token immediately 401'd, both admin logins returned 403, and the disabled `admin2` still counted as an admin (the subsequent role change could not even authenticate). The documented recovery (`_create_default_admin`, web/app.py:436-439) does nothing because the `admin` row still exists (it is merely disabled), so recovery requires direct DB surgery. Fix: count only `enabled=1`, and apply the guard to `enabled` transitions or refuse self-disable when no other enabled admin remains.
  - [high] **A single-scope API key can convert itself into a full admin account.** `require_auth` admits a key holding exactly `post:/api/v1/admin/users` (web/app.py:587-616), and `create_user` never checks that the requested role is within the key's delegated authority (`_require_within_delegation` is called only on key-management routes, web/app.py:1921-1923, 1967-1968). Verified: an admin minted a key with only that one scope; the key created `pwnadmin` with `role: "admin"` (201), `POST /api/auth/login` for that account returned 200, and the resulting session listed API keys (200). The same holds for `put:/api/v1/admin/users/{user_id}/password`: reset an admin's password, log in as that admin. This directly contradicts the stated model that “a key with one route's permission gains nothing on any other route” (web/permissions.py:20-24). User-management permissions are therefore equivalent to `admin:*`; they should be treated as non-delegable, or `create_user` must forbid `role=admin` and password reset must exclude admins for key principals.
  - [high] **Renaming the bootstrap `admin` account causes the next restart to silently re-create `admin`/`admin`.** `update_user` allows renaming any user, including the bootstrap account, with no protection (web/app.py:2093-2101); `_create_default_admin` keys solely on the literal username `admin` (web/app.py:444-453). Verified: rename id 1 `admin` → `owner` (200), call `_create_default_admin()` (the startup path) → a new row `admin`/`admin` is inserted and `POST /api/auth/login {"admin":"admin"}` returns 200. An operator who renamed the seed account (or a migration did) silently reopens the documented default credential; nothing marks it `must_change_password` server-side. Fix: make the bootstrap idempotent on a stable marker (e.g. a settings row or `created_by='bootstrap'`), and refuse/warn on renaming the seed account.
  - [medium] **Mutations are audited as `system`, so there is no attributable record of who changed privileges.** All four calls use `_log(..., "users")` without `user=` (web/app.py:2008, 2035, 3430, 3451), and `_log` defaults to `"system"` (web/app.py:233-236). Verified: `[system] [users] …` for create, role change, password change and delete. The role change records the target id and transition but not the target's name; the password reset records only the id; create records the (attacker-controlled) username but no id. The only actor signal is the adjacent HTTP middleware line (web/app.py:1280), which `viewer` can read via `/api/logs` and which does not say what changed. A durable audit row with `(actor, actor_type, target_id, action, old/new role)` is missing.
  - [medium] **`create_user` performs no username validation, and the mismatch with login's `strip()` makes some accepted accounts permanently unusable while enabling log forging.** `create_user` checks only truthiness (web/app.py:3406), while `login` does `str(payload.get("username","")).strip()` (web/app.py:1574); `update_user` caps at 128 (web/app.py:2094) but `create_user` does not. Verified acceptances: a 300-character username (201, stored intact on SQLite), `"аdmin"` with a Cyrillic `а` (201), `"Admin"` (201, case-sensitive duplicate), `"admin "` with a trailing space (201 — but login strips it and returns 401, so the account can never authenticate), and `"line\nbreak"` (201). The newline is interpolated verbatim into `_log` (web/app.py:3430), producing a forged `[system] [users]` line in `LOG_BUFFER`, which `viewer` can read (`GET /api/logs`, test_auth_rbac.py:381). Fix: normalize/strip consistently between create/update/login, bound to 1..128, restrict to a documented charset, reject control characters, and reject usernames that case-fold or NFKC-fold to an existing name.
  - [medium] **The last-admin check is a non-atomic read-then-write, so two concurrent demotions can remove every admin.** The `COUNT(*)` (web/app.py:1457-1459) and the `UPDATE`/`DELETE` (2031-2033, 3447-3449) are separate statements with no `SELECT … FOR UPDATE`, serializable transaction, or conditional `UPDATE … WHERE (SELECT COUNT(*) …) > 1`. On PostgreSQL READ COMMITTED (or MySQL REPEATABLE READ) two admins demoting/deleting each other can both observe 2 and both succeed. Unverified by probe (SQLite serializes the writers); the equivalent single-admin case is correctly 409 (existing test).
  - [medium] **Password policy is a bare 8-character minimum with no self-service rotation, and the brief's `POST /api/v1/auth/password` does not exist.** Only `len >= 8` is checked on both paths (web/app.py:1987-1988, 3410-3411); verified `"        "` (eight spaces) and a 10,000-character password are both accepted (201). There is no maximum, no common-password check, and no requirement of the old password anywhere. Consequently a non-admin can never rotate their own password: the only mutation is the admin-only `PUT /api/v1/admin/users/{user_id}/password` (permissions.py:76-97), and `POST /api/v1/auth/password` is 404 (verified). The hash itself is sound — PBKDF2-HMAC-SHA256, 260k iterations, 16-byte random salt, `hmac.compare_digest` (web/app.py:315-342). Fix: add a self-service route that requires the old password and revokes other sessions, keep an admin reset path, and bound password length (e.g. 8..1024) with a whitespace/entropy check.
  - [low] **`delete_user` leaves orphan session rows even when the rowid is not reused.** The row count for the deleted user persists (verified: `(6, 1)` after the delete), so the table accumulates credentials that are only rejected because the join fails. Combined with any future id reuse (manual insert, restore, import, another DB's sequence reset) the critical finding above recurs; a cascade delete is the real fix, not a join.
  - [low] **Every INSERT error is reported as 409 “username already exists”.** The broad `except Exception` at web/app.py:3423-3424 hides length/constraint/connection errors and returns a misleading status; on a backend enforcing `String(128)` an over-long username will look like a duplicate. The subsequent `SELECT` in the same (possibly failed) transaction can also surface as 500 instead of the intended 409 (unverified on PostgreSQL).
  - [low] **`update_user` validates `role` after it has already written the username.** web/app.py:2093-2101 persists the rename, then 2103-2105 rejects an invalid role; because the rename `UPDATE` is in the same transaction and the HTTPException aborts before `commit()`, nothing is persisted — but only because the exception path closes the uncommitted connection. Any future use of a session with autobegin/autocommit, or a driver that commits per statement, would make this a partial update. Validate all inputs before the first write.
  - [nit] Role values are correct and fail closed, but `change_user_role` strips whitespace while `create_user` (Pydantic) and `update_user` do not, so `" admin "` is usable in one path and a 400 in another; pick one normalization rule.
  - [nit] `create_user` returns 201 with no `Location`, no `created_at`, and no indication that the caller should force a password change; `delete_user` returns `{"ok": true}` with no information about revoked sessions (there are none — see critical).
  - **Verified sound (no finding):** role demotion is enforced per request because the role is re-read from the joined row (web/app.py:477-498) — a demoted operator's existing token is immediately a viewer (probe P1); password reset revokes all sessions (web/app.py:2003-2005, existing test); disabling a user deletes their sessions and blocks login 403 (web/app.py:484-490, 1597-1599); unknown roles are rejected by both the handlers and the fail-closed permission map; duplicate usernames are rejected 409; CSRF/same-origin is applied to all four handlers and to bearer keys; the password hash uses a fresh salt per change and a timing-safe comparison.
- **Tests that should exist:**

## issue_s3_credentials — POST /api/v1/admin/s3-credentials

- **Handler:** web/app.py:5103 (route declared web/app.py:5099-5102). The edit endpoint `update_s3_credentials` — PUT `/api/v1/admin/s3-credentials/{identifier}` — is covered in the same report: web/app.py:5186 (route 5182-5185), store logic `S3CredentialStore.update` teledrive/s3/credentials.py:288.
- **Auth model:**
  - **Session cookie principal:** must hold role `admin`. Both `/api/v1/admin/s3/credentials` and the legacy `/api/v1/admin/s3-credentials` are in `_ADMIN_ONLY_PREFIXES` (web/permissions.py:79-80), so `is_admin_only()` returns true for every method (web/permissions.py:129-143), `_required_roles` returns `_ROLE_ADMIN` (web/app.py:524-525), and a `viewer`/`operator` session is rejected 403 before the handler (web/app.py:531-536), so only an admin session reaches it.
  - **Bearer API-key principal:** there is **no role gate** — the key branch of `require_auth` (web/app.py:587-622) passes iff the key is active and holds the canonical route permission `post:/api/v1/admin/s3/credentials` (or the alias's `post:/api/v1/admin/s3-credentials`). Verified with a key minted with only that scope: `POST` returned 201. The key needs no S3 permission of its own, because API-key scopes are REST route names and S3 permissions are a separate vocabulary.
  - **Delegation ceiling: absent.** `_require_within_delegation` and `_require_within_lifetime` (web/app.py:1863-1911) are called only from `/api/v1/admin/keys` (web/app.py:1921-1923, 1949, 1967). Neither the S3 create handler (web/app.py:5103-5119) nor the update handler (web/app.py:5186-5207) calls them, and there is no S3-specific subset check anywhere. Unlike key issuance, the caller's authority cannot be compared to the requested `s3:*` set because the two vocabularies do not intersect.
  - **CSRF / same-origin:** `_same_origin` is called on both writes (web/app.py:5105, 5189), requiring `x-teledrive-csrf: 1` and, when `Origin` is present, an exact `Host` match (web/app.py:300-312). GET list/reveal need no CSRF.
  - **Reveal contrast:** `GET …/{identifier}/secret` deliberately refuses API keys and is session-only because revealing another credential's secret "bypasses the delegation ceiling" (web/app.py:5129-5147). `POST` re-opens that hole: it returns a **new** secret with arbitrary permissions to the same key principal.
- **Inputs:**
  - **Create:** `S3KeyCreateRequest` (web/app.py:1408-1411):
    - `name: str`, `Field(min_length=1, max_length=120)`. Pydantic checks the raw value; the store strips and re-checks `1 <= len(name.strip()) <= 120` (teledrive/s3/credentials.py:182-183). No charset restriction — newlines/NUL/control characters are accepted and persisted (probe: 201).
    - `permissions: list[str]`, `default_factory=lambda: list(DEFAULT_PERMISSIONS)` (web/app.py:1410) — omitting the field grants **all 90** S3 permissions (probe: 201, 90 entries, including `s3:PutBucketPolicy` and `s3:DeleteBucket`). Every entry must be an exact member of `PERMISSIONS` (`DEFAULT_PERMISSIONS` is just that set sorted, teledrive/s3/credentials.py:34-111, 184-186); empty list, non-list, duplicate entries (deduped by `sorted(set(...))`, line 194) and unknown strings are rejected. There is no `extra="forbid"`, so `tags`, `revoked`, `id` and other unknown fields are silently discarded (probe: 201, id is a fresh UUID).
    - `expires_at: int | None`: Unix seconds. Store requires `now < expires_at <= now + 10*365*86400` (teledrive/s3/credentials.py:187-188). `None` = never expires. Pydantic lax mode coerces `true`→1 and numeric strings; a fractional float is rejected. No timezone concept.
  - **Update:** `payload: dict = Body(...)` (web/app.py:5187) — **no Pydantic model**, so no schema, no bounds and no type checking at the edge. The store applies:
    - `name`: stripped, non-empty, `<= 128` characters (teledrive/s3/credentials.py:307-311) — eight characters **more** than the create limit and the `String(120)` column (teledrive/s3/credentials.py:23).
    - `permissions`: non-empty list of exact `PERMISSIONS` members, replaced wholesale (teledrive/s3/credentials.py:312-317).
    - `expires_at`: `int(expires_at)` with **no bounds at all** (teledrive/s3/credentials.py:318-319) — past, zero, negative and arbitrarily far future are all accepted. `clear_expiry: true` sets it to `NULL` (line 320-321).
    - `tags`: the store supports it (teledrive/s3/credentials.py:322-323) but the handler never passes it (web/app.py:5194-5200); the create model has no `tags` field either. ABAC principal tags are therefore unmanageable through the API.
    - At least one recognised key is required, else 422 "Nothing to update" (teledrive/s3/credentials.py:324-325).
  - **`identifier`:** exact match against `id` **or** `access_key` (`WHERE id = :identifier OR access_key = :identifier`, teledrive/s3/credentials.py:298-301, same at 269-270 for reveal). `id` is `uuid4()` (36 chars) and `access_key` is `"TD" + token_hex(12).upper()` (26 chars, teledrive/s3/credentials.py:191-192), so the two forms cannot realistically collide. No prefix matching. Update and revoke impose **no length or format bound**; reveal does (`1..200`, web/app.py:5148). SQL is parameterised.
- **Side effects:**
  - **Create:** one `INSERT` into `storage_s3_credentials` with a UUID id, `access_key`, `encrypted_secret = Fernet(master).encrypt(secret)`, JSON permission list, `created_at`, `expires_at`, `revoked=False`, JSON tags (teledrive/s3/credentials.py:195-201) and one `commit()` (line 201). The master key is mandatory: `load_master_key` raises `RuntimeError` for a missing/short/invalid key (teledrive/s3/credentials.py:147-160) and the handler maps that to 503 (web/app.py:5112-5113). `S3CredentialStore.__init__` runs `ensure_schema()` first (teledrive/s3/credentials.py:172-176).
  - The plaintext secret exists only in the local variable and the 201 body (`{"id","access_key","secret_key","permissions"}`, web/app.py:5116-5117). `Cache-Control: no-store` is applied globally to `/api/*` (web/app.py:1361-1364). It is stored encrypted and is never returned by `list()` (explicit column list, teledrive/s3/credentials.py:204-212).
  - **What the secret can do:** every granted `s3:*` permission on the S3 data plane — with the default set, that includes `s3:DeleteBucket`, `s3:PutBucketPolicy`/`DeleteBucketPolicy`, ACL ownership controls, replication, website and lifecycle configuration. Bucket policy/ACL/ABAC still intersect at the data plane, but the credential is itself a valid policy principal.
  - **Update:** one `UPDATE … WHERE id = :id` (teledrive/s3/credentials.py:326-327) and `commit()`, then a re-read via `list()` (line 329-330). Name, permissions and expiry change; `access_key` and `secret` never do (docstring lines 293-297). The response is `{"ok": true, "credential": <list row>}` (web/app.py:5205) — metadata only, `encrypted_secret` is not selected and the secret is not returned.
  - **Audit:** neither handler calls `_log`. The only record is the framework `_audit_log_middleware` line `METHOD /path from <ip>` with `user=<username or api-key name>` (web/app.py:1288-1297) and its status line (1304-1305). The created credential's id, access key and permission set are not recorded anywhere. Probe: after create/update/revoke, the buffer contained only `[http]` lines; no `api-keys`/`security` entry names the new credential. The secret itself is never logged.
- **Failure modes:**
  - 401 — no session and no bearer credential (web/app.py:632-636).
  - 403 — non-admin session (web/app.py:531-536); API key invalid/expired/revoked/lacking the route permission (web/app.py:617-622); missing `x-teledrive-csrf` or cross-origin `Origin` (web/app.py:300-312); API key on the reveal route (web/app.py:5140-5147).
  - 422 (Pydantic) — create body: `name` type/length, `permissions` not a list of strings, `expires_at` fractional float (web/app.py:1408-1411).
  - 422 (store `ValueError`, re-emitted verbatim, web/app.py:5114-5115, 5203-5204) — whitespace-only or >120-char create name; empty/unknown permission on create or update; create expiry in the past or beyond ten years; update of an unknown identifier; update of a revoked credential; update with no recognised field; update name >128; update `expires_at` non-numeric.
  - 404 — only from `DELETE` (web/app.py:5223-5224) and only for an id it does not find; update/reveal answer an unknown identifier with **422**, not 404.
  - 503 — `load_master_key` raised `RuntimeError` (invalid/unset key material) (web/app.py:5112-5113, 5201-5202).
  - 500 — **`OSError` from `load_master_key` is not caught** on create, update, list or revoke (only reveal catches it, web/app.py:5165-5170): a missing `TELEDRIVE_S3_MASTER_KEY_FILE` raises `FileNotFoundError` (teledrive/s3/credentials.py:151) and the client gets a bare 500 (verified). The audit middleware then logs `EXCEPTION: FileNotFoundError: ... '/path/to/master.key'` (web/app.py:1301), exposing the key-file path in the viewer-readable buffer — precisely what reveal's handler was hardened to avoid. Any `SQLAlchemyError` (e.g. the unique `access_key` constraint, teledrive/s3/credentials.py:24) is likewise an unhandled 500; parameter text (ciphertext, access key) reaches the log, but not the plaintext secret.
  - No 409, no 429, no `Location` header, no expiry/revocation-specific status.
- **Findings:**
  - [critical] **No delegation ceiling: any API key holding one route permission can mint a full-power S3 credential and receive its plaintext secret.** `require_auth` admits an API key for `post:/api/v1/admin/s3/credentials` (web/app.py:587-622), and the handler passes `payload.permissions` straight to the store (web/app.py:5109-5111) without calling `_require_within_delegation`/`_require_within_lifetime` (contrast key issuance, web/app.py:1921-1923). Verified: a key minted with only `post:/api/v1/admin/s3/credentials` (plus the put/delete route scopes) POSTed `{"name":"escalated"}` and got **201 with all 90 permissions including `s3:PutBucketPolicy` and `s3:DeleteBucket`, plus the `secret_key`**. The same key is correctly 403 on `GET …/{identifier}/secret`, which makes the reveal hardening moot: create is an unbounded secret-issuance path for the principal that reveal refuses. The update handler has the same gap: `PUT` can replace any credential's permission set with any `s3:*` set (web/app.py:5194-5200, teledrive/s3/credentials.py:312-317). Verified: a credential issued with `s3:GetObject` was edited to `s3:GetObject + s3:DeleteBucket + s3:PutBucketPolicy` (200) by an API-key principal that held no S3 permission. A credential's secret does not change, so an attacker who already knows their own credential's secret can escalate it in place; an attacker who does not still escalates the authority handed to whoever holds it.
  - [high] **Omitting `permissions` grants every S3 permission, including destructive and governance actions.** `S3KeyCreateRequest.permissions` defaults to `list(DEFAULT_PERMISSIONS)` (web/app.py:1410) — all 90 names (teledrive/s3/credentials.py:34-111). Verified: `POST {"name":"x"}` returned 201 with `s3:DeleteBucket`, `s3:PutBucketPolicy`, `s3:PutBucketReplication` etc. A least-privilege API whose empty request produces the most powerful credential is insecure by default; the UI warns about "risky" selections but the server never requires an explicit choice.
  - [high] **`update` has no expiry bounds and can resurrect an expired credential.** `S3CredentialStore.update` accepts `expires_at` with no validation (teledrive/s3/credentials.py:318-319), unlike `create` (lines 187-188). Verified: `PUT {"expires_at": 1}` returned 200 and stored `1`; `PUT {"expires_at": now+20y}` returned 200 and stored a timestamp beyond the documented ten-year cap. More seriously, update only checks `revoked`, never `expires_at` (lines 298-305), so an expired credential — whose secret `reveal` explicitly refuses to hand out (lines 275-279) and which `resolve` refuses to authenticate (line 235) — can be un-expired with its original access key and secret. Verified end-to-end: create with a 2-second expiry, wait, `resolve()` returns `None`; `PUT {"expires_at": now+1h}` returns 200; `resolve()` then returns the **same original secret**. Expiry is enforced at signature-verification time (`store.resolve` is the `lookup_secret` passed to `verify_header_signature`, web/s3.py:4782, teledrive/s3/sigv4.py:262-264, credentials.py:235), so the revival is real access, not cosmetic.
  - [high] **Credential issuance and editing are unaudited.** Neither handler calls `_log` (web/app.py:5103-5119, 5186-5207); the reveal handler, by contrast, writes an actor-tagged `security` line (web/app.py:5175-5176). The framework only records `POST /api/v1/admin/s3/credentials from <ip>` and `PUT /api/v1/admin/s3/credentials/<id> from <ip>` with the actor (web/app.py:1288-1297); the new credential's id, access key, permission set and expiry are nowhere in the log, so "who created this full-power key" and "what did it grant" cannot be answered from the audit trail. Verified: after a create that returned a 90-permission credential, no non-`http` line mentioned it. Names are not logged, so there is no log-forging vector from the name here, but there is also no record.
  - [medium] **A missing master-key file returns 500 and leaks the key path to lower-privileged log readers.** `load_master_key` uses `os.open(secret_file, ...)` (teledrive/s3/credentials.py:147-153); create/update/list/revoke catch only `RuntimeError` (web/app.py:5112, 5201, 5093, 5221). Verified with `TELEDRIVE_S3_MASTER_KEY_FILE` pointing at a nonexistent file: `POST`, `PUT` and `GET` all returned `500 Internal Server Error`. The middleware formats `str(exc)` into `LOG_BUFFER` (web/app.py:1301), so the configured master-key path is written to a buffer that `viewer` sessions can read via `/api/logs` (web/app.py:3358). Reveal already handles this correctly (web/app.py:5165-5170). Credentials still fail closed (nothing is created), but the error class and information disclosure are wrong.
  - [medium] **`update` accepts a 128-character name while the column and `create` allow 120.** teledrive/s3/credentials.py:309 (`<= 128`) vs line 23 (`String(120)`) and line 182 (`<= 120`). Verified on SQLite: `PUT {"name": "n"*128}` returned 200 and stored all 128 characters. On MySQL (the production target) this is either a truncation or a `Data too long` 500, and the API's own two endpoints disagree on the maximum. A client cannot know which bound applies.
  - [medium] **The identifier contract is inconsistent and unbounded.** `update` and `reveal` match `id OR access_key` (teledrive/s3/credentials.py:298-301, 269-270), but `revoke` matches `id` only (teledrive/s3/credentials.py:332-335). Verified: `PUT …/<access_key>` returned 200 while `DELETE …/<access_key>` returned 404 on the same credential. Update and revoke have no length bound at all; a multi-kilobyte identifier reaches SQL. Unknown identifiers are 422 on update/reveal but 404 on revoke, and update distinguishes "unknown" (422 "Unknown credential") from "revoked" (422 "Revoked credentials cannot be edited"), giving a put-scoped key an existence/state oracle over credentials it cannot list.
  - [medium] **ABAC principal tags cannot be set or edited through either endpoint.** The table and store support `tags` (teledrive/s3/credentials.py:32, 115-126, 189, 322-323), and the S3 gateway evaluates `aws:PrincipalTag/*` from them (`principal_tags`, lines 214-224), but `S3KeyCreateRequest` has no `tags` field (web/app.py:1408-1411) and the update handler never passes `payload["tags"]` (web/app.py:5194-5200). Operators can only populate tags by direct DB access or an internal caller. Policy conditions on principal tags therefore silently evaluate to "no tags" for every API-created credential.
  - [low] **`update` racing `revoke` can modify a revoked row.** `update` reads `(id, revoked)` (teledrive/s3/credentials.py:298-305), then issues `UPDATE … WHERE id = :id` with no `revoked = 0` predicate (lines 326-327). If a revoke commits between the read and the write, the edit still succeeds and returns `revoked: true`; the credential stays dead because `resolve` checks `revoked`, so this is integrity/cosmetic rather than an access resurrection. A conditional `WHERE revoked = 0` with a `rowcount` check would make the "Revoked credentials cannot be edited" contract atomic.
  - [low] **The create response withholds exactly the fields an operator needs to confirm the grant.** It returns `id`, `access_key`, `secret_key`, `permissions` only (web/app.py:5116-5117) — no `name`, `expires_at`, `tags` or `revoked`, and `POST {"expires_at": …}` cannot be verified from the response (verified: setting a 2-second expiry produced a 201 body with no `expires_at`). There is no `Location` header. Combined with silently ignored unknown fields, a caller cannot tell whether `{"tags": …}` was honoured (it was not).
  - [low] **`name` accepts control characters and newlines.** Create strips but does not validate the charset (teledrive/s3/credentials.py:182-183); the same is true of update (307-311). Unlike `issue_api_key`, the name is not written to the audit log, and the WebUI renders it with `x-text` (web/static/credentials.html:417, 451; web/static/s3-governance.html:138), so this is hygiene/data-quality rather than log forging or stored XSS. A charset check (printable, no C0/C1) would still be appropriate for a field echoed into CLI configs (rclone).
  - [low] **Concurrent creates can only collide on the random access key, and that collision is a 500.** `access_key` is `"TD" + token_hex(12).upper()` with 96 bits of entropy (teledrive/s3/credentials.py:192) under a UNIQUE constraint (line 24); two independent creates therefore do not race on a caller-supplied value, but a collision or any other DB error raises an uncaught `IntegrityError` and returns 500 with the statement in the log. `unverified`: MySQL's exact behaviour under concurrent writes to the unique index was not exercised.
  - [nit] The two spellings are separate permissions (`post:/api/v1/admin/s3/credentials` vs `post:/api/v1/admin/s3-credentials`), so an operator granting "create S3 credentials" must grant it twice for the documented permanent alias to work for API keys (web/permissions.py:194-197; same issue already reported for reveal).
  - [nit] Error shapes are inconsistent: Pydantic 422s return `detail: [{...}]`, store 422s return `detail: "…"` (web/app.py:5115, 5204), and revoke alone returns 404. `payload: dict = Body(...)` also hides every update bound from OpenAPI.
  - **Verified sound (no finding):** permission names are validated against the live `PERMISSIONS` set on both create and update (teledrive/s3/credentials.py:184-186, 312-316), so an arbitrary string cannot be stored; `resolve` independently rejects a permission outside the set and fails closed on a bad ciphertext (lines 229-242), so an unknown permission can never authenticate. Secret entropy is adequate (`secrets.token_urlsafe(40)`, ~320 bits; access key 96 bits, lines 192-193) and the secret is Fernet-encrypted at rest with a mandatory master key (lines 147-160, 195-200); a losing key makes decryption fail closed, not leak. The secret is returned once at create, never by `list()` (204-212) or by `update` (329-330), never appears in error text, and `Cache-Control: no-store` is set. Expiry is enforced at SigV4 header and presigned verification via `resolve` (credentials.py:235, sigv4.py:262-264), with a 15-minute clock-skew window (sigv4.py:356-362); revoked credentials are rejected by both `resolve` and `is_active` (credentials.py:235, 257). Session role gating is structural (web/app.py:524-536) and CSRF/same-origin on both writes held under probe. The WebUI warning about risky permissions is honest about granting rather than blocking (web/static/credentials.html:281-285), which is consistent with an admin-only session, but not with a route-scoped API key.
- **Tests that should exist:**
  - `test_api_key_cannot_issue_or_edit_s3_credentials` — mint a key with only `post:/api/v1/admin/s3/credentials` and `put:/api/v1/admin/s3/credentials/{identifier}`; assert POST returns 403 and no row exists, and PUT against an existing `s3:GetObject` credential returns 403 with its permissions unchanged **(mandatory regression; today both are 201/200, verified)**.
  - `test_issuing_without_permissions_is_not_full_power` — `POST {"name": "x"}` must 422 "permissions required" (or grant at most an explicit read-only default); assert the response never implies `s3:DeleteBucket`/`s3:PutBucketPolicy` without an explicit request.
  - `test_s3_permissions_cannot_exceed_the_caller` — a session admin may grant anything; a bearer key must only grant S3 authority it demonstrably holds (today a key holds none, so any non-empty `permissions` must be refused), and the audit line must name the refusal.
  - `test_update_expiry_rejects_past_and_over_ten_years` — `PUT {"expires_at": 1}`, `{"expires_at": 0}`, `{"expires_at": now+20y}` all return 422; only `now < t <= now+10y` and `clear_expiry` succeed.
  - `test_expired_credential_cannot_be_revived_by_update` — create with `expires_at = now+1`, sleep, assert `resolve()` is `None`; `PUT {"expires_at": now+1h}` must 422/409 and `resolve()` must stay `None`.
  - `test_create_and_update_write_an_actor_tagged_audit_line` — assert the `security`/`api-keys` log contains the actor, the credential id, the access key prefix and the permission set, contains no `secret_key`, and is written only after a successful commit.
  - `test_missing_master_key_file_returns_503_and_logs_no_path` — point `TELEDRIVE_S3_MASTER_KEY_FILE` at a nonexistent path; assert create/update/list return 503 with a fixed message, and that `LOG_BUFFER` contains neither the path nor the exception text.
  - `test_update_accepts_the_same_identifier_forms_as_delete` — PUT and DELETE by `id` and by `access_key` must both succeed (or both 404 with the same body); today PUT-by-access is 200 and DELETE-by-access is 404.
  - `test_update_rejects_a_name_longer_than_create_and_the_column` — a 121-character name returns 422 on both endpoints, and a 128-character one never reaches the DB.
  - `test_create_and_update_response_never_contains_the_secret` — create lists the secret once; update and list must not; assert `secret_key` and the encrypted blob are absent from every 200 body and from `Cache-Control` cacheable responses.
  - `test_principal_tags_round_trip` — create and update with `tags` must persist them (or the field must be absent from the store API); assert `principal_tags(access_key)` reflects the API request.
  - `test_concurrent_update_and_revoke_leave_the_row_revoked` — race PUT against DELETE; assert the final row has `revoked=True`, that no update returns 200 after the revoke commits, and that `resolve()` is `None` either way.
- **Verdict:** Secret storage, entropy, permission-name validation and SigV4-time expiry enforcement are sound, but authorization is not: one route-scoped API key can mint a 90-permission S3 credential and walk away with its secret, `PUT` can add those permissions to any credential, expiry can be set into the past or beyond the documented cap (or used to revive an expired key), and neither issuance nor editing is audited.

## get_object_content — GET /api/v1/buckets/{bucket}/content

- **Handler:** `web/app.py:5526` (route declared `web/app.py:5524-5525`), metadata twin `head_object_content` at `web/app.py:5503` (route `5501-5502`), shared range parser `_byte_range` at `web/app.py:1541-1562`, engine `TelegramObjectStorage.iter_bytes` at `teledrive/storage/engine.py:612-704`, per-chunk verified fetch `_verified_fetch` at `engine.py:590-610`. Unlike PUT, there is no shared core with the session twin: the S3-browser download at `web/app.py:3606-3657` is a near-duplicate of this handler (same `_byte_range` call, same header block) and has the same defects.
- **Auth model:** exactly one principal, no second gate.
  - **Principal:** a bearer API key. `require_api_scope("rest:objects:get")` (`web/app.py:5528` → `1566-1579`) validates the token with `ApiKeyStore.authorize` (`teledrive/api_keys.py:207-224`). Missing/non-Bearer credentials → 401 + `WWW-Authenticate: Bearer` (`app.py:1569-1571`); invalid/expired/revoked key or missing scope → one generic 403 (`app.py:1577-1578`). No session, role, CSRF or `_same_origin` path is involved, and no `require_auth` call exists on either route.
  - **Scope granularity:** exact-name membership only (`api_keys.py:218` over `expand_scopes`), so `rest:objects:get` does **not** imply `rest:objects:head`. Verified in `tests/web/test_api_keys.py:98-99`: a `rest:objects:put`-only key is rejected for both; `objects:read` expands to exactly get/head/list/list-versions (`tests/web/test_api_keys.py:117-119`, groups at `api_keys.py:103-104`), and `admin:*` grants both (`api_keys.py:112-133`).
  - **Cross-bucket leakage — by design, and total:** the scope is tenant-global. `bucket` is only used as a lookup key (`app.py:5535` → `teledrive/storage/catalog.py:547-558`); nothing scopes a key to a bucket, prefix or owner. Any key holding `rest:objects:get` reads every byte of every bucket, and any key holding `rest:objects:head` enumerates size/SHA-256/object-id of every key in every bucket. There is no object-level authorization at all: `BucketPolicyStore`, `BucketAbacStore` and object ACLs are never consulted, while the S3 data plane evaluates all three at one decision point (`web/s3.py:2782-2818`) called for every request before routing (`web/s3.py:4826-4831`).
  - **Can a read-only principal write?** Not data. But `authorize` performs `UPDATE api_keys SET last_used_at` + `commit()` on *every* request (`api_keys.py:220-223`), and the audit middleware resolves the key name with two more short-lived connections (`app.py:190-230`, called at `1297`).
- **Inputs:**
  - `bucket` — path segment, plain `str` with no `pattern`/`max_length`, no `BucketCatalog.validate_bucket` call. Invalid names simply miss the head lookup and 404; there is no separate "bucket exists" check, and a nonexistent bucket is reported as `404 Object not found` rather than S3's `NoSuchBucket`.
  - `key` — required query parameter `min_length=1, max_length=1024` (`app.py:5527`). Pydantic counts **characters**; the store requires **1..1024 UTF-8 bytes** (`catalog.py:149-150`). A 600-character non-ASCII key (1200 bytes) passes the route and raises an uncaught `ValueError` at `catalog.py:548` → **500** (`app.py:5534-5537` catches only `FileNotFoundError`). No `AllowUnicode` control, no NUL/control-character rejection; the key never reaches a filesystem path.
  - `Range` — single header, parsed by `re.fullmatch(r"bytes=(\d*)-(\d*)")` after `.strip()` (`app.py:1545`). Accepted forms: `a-b`, `a-`, `-n`. Everything else (`units=`, multi-range `0-1,4-6`, `--1`, `+1-2`, `0x10-20`, `--`) → 416 with `Content-Range: bytes */size` (`app.py:1546-1547`). Empty object + any `Range` → 416 (`1549-1551`). `-0` → 416 (`1553-1555`). Suffix longer than the object clamps to the whole object (`1556`). `start >= size` → 416 (`1560-1561`). Arithmetic is plain Python `int`, so no overflow/underflow and no preallocation from the header: probed `bytes=0-9223372036854775808` → `(0,16,True)` and `bytes=99999999999999999999-` → 416 for a 16-byte object. Trailing `\n`/space is stripped, so `bytes=0-1\n` is accepted.
  - **Not accepted:** `If-Match`, `If-None-Match`, `If-Modified-Since`, `If-Range`, `x-amz-server-side-encryption-customer-*` (SSE-C), `response-content-type`/`response-content-disposition`, `versionId`, `partNumber`, `x-amz-checksum-mode`. Zero references in `web/app.py`; the S3 route supports preconditions (`web/s3.py:3930-3937`) and parses SSE-C headers (`3895-3907`).
  - `Authorization` — ≤200 chars, must start `td_live_` (`api_keys.py:209-211`). `Host` — must be in `ALLOWED_HOSTS` (`app.py:1262-1269`). No request body is read.
- **Side effects:** read-only in the data plane; nothing is written to `storage_objects`, and no bytes go to Telegram.

- **Findings:**
  - [high] **The archive/restore gate is absent, so a "GLACIER-class" object is served without a restore.** The S3 surface refuses with `403 InvalidObjectState` when `catalog.object_read_state(...)["archived"]` is true (`web/s3.py:3916-3926`, state computed at `teledrive/storage/catalog.py:239-265`), for both GET and HEAD. This handler never calls `object_read_state` (grep: zero matches for `storage_class`/`restore_until`/`InvalidObjectState` in `web/app.py`) and streams the archived bytes with 200/206 regardless. So an operator's tiering policy (`docs`-level intent, `teledrive/s3/tiering.py:25-48`) is enforced on `boto3` but silently ignored by the REST bearer surface: no restore needed, no restore-window check, no `x-amz-restore` header, and HEAD reports a normal 200 for an object S3 calls unreadable.
  - [high] **SSE-C objects produce a 200 with an empty body, and their plaintext SHA-256 is advertised without a key.** `iter_bytes` requires `sse_key` for any object with an encryption marker and raises `SSECError` otherwise (`engine.py:632-636`); this handler never parses or forwards a customer key (`app.py:5538-5550`), so a misconfigured or unaware client gets `200` + `Content-Length: N` + `ETag: "<plaintext sha256>"` and **zero bytes** (probe above). Before that, `head_object_content` returns 200 with the same plaintext digest and size (`app.py:5513-5519`). The S3 surface, by contrast, rejects the request with `400 InvalidRequest` *before* any header, and deliberately publishes the ciphertext ETag instead of the plaintext digest (`web/s3.py:3896-3907`, `_effective_object_etag` at `233-241`). Two consequences: a backup restore tool that trusts the 200 writes an empty file over good data, and any `head`-scoped key can confirm the plaintext hash of an encrypted object it cannot read.
  - [high] **Bucket policy, ABAC and object ACLs are not evaluated, so an explicit `Deny` cannot stop a read.** The only checks are token scope and head existence (`app.py:5534-5538`); `BucketPolicyStore`/`BucketAbacStore`/`object_acl` appear only in `web/s3.py` (definition `2782-2818`, applied to every request including GET/HEAD at `4826-4831`). A bucket policy `Deny s3:GetObject` with `Principal:"*"` blocks boto3 and does not block `GET /api/v1/buckets/{bucket}/content` with any `rest:objects:get` key — including the same key an operator believed was constrained. This is the read-side half of the PUT finding; together they make the bucket-policy layer advisory for the entire REST surface.
  - [medium] **A read can hold or leak a pooled DB connection.** The connection opened at `app.py:5530` is checked out for the whole transfer — including multi-minute Telegram downloads — while the pool is 15 connections total (`teledrive/db.py:551`, probed `QueuePool(5, 10, 30s)`), and every request also needs connections for auth (`app.py:1572`) and the log line (`app.py:201-226`). Fifteen concurrent slow downloads therefore starve every other request (30 s pool timeout, then 500), and the early-disconnect path skips the explicit close entirely (probe in Failure modes), leaving it to GC. Nothing bounds concurrent reads, so this is reachable by a single get-scoped key.
  - [medium] **REST reads are invisible to access accounting, which then demotes actively read data to archive.** `record_object_access` is called only from `web/s3.py:3940`; neither handler here calls it (grep: only definition `catalog.py:267` and that call site). Tiering's idle clock is `COALESCE(last_accessed_ns, created_at)` (`teledrive/s3/tiering.py:502-505`), so an object read daily through REST is treated as never read and can be moved to `ARCHIVE_ACCESS`; the next S3 GET then fails with 403 until a restore. Access stats (`object_access_stats`, `catalog.py:281-298`) are likewise wrong for REST-only workloads.
  - [medium] **No conditional request support turns a resumed range into a silent splice of two object versions.** Because `ETag` is the full-object digest and `If-Range`/`If-Match` are ignored (`app.py:5512-5560`), a client that saves a partial download, lets the key be overwritten, and resumes with `If-Range: "<old etag>"` gets a `206` for the *new* head and appends the wrong bytes; the only defence is the caller re-hashing the final file. The S3 surface at least evaluates `If-Match`/`If-None-Match`/`If-(Un)Modified-Since` before any Telegram traffic (`web/s3.py:3930-3937` → `teledrive/s3/conditions.py:35-61`), though it does not implement `If-Range` either; REST implements none of them, so the two surfaces disagree on resumability and neither can refuse a stale range.
  - [medium] **The ETag is not comparable across surfaces and is wrong for multipart objects.** This handler always advertises `item.sha256` (`app.py:5556`, `5514`); the S3 surface advertises `_effective_object_etag` — the multipart `-N` layout digest, or the ciphertext ETag for SSE-C (`web/s3.py:233-241`). A client that uploads multipart via S3 and reads via REST (or caches the ETag from one surface and validates on the other) sees two different ETags for identical bytes; any `If-Match`-style workflow built on the REST value breaks. On a partial response the full-object ETag is itself correct S3/HTTP behaviour (S3 keeps the same ETag across ranges), so the range aspect is not the defect — the cross-surface value is.
  - [medium] **A multi-byte key over 1024 UTF-8 bytes is a 500 on a read.** `key="é"*600` (1200 bytes) passes the 1024-character route bound and hits `catalog.py:149-150`; only `FileNotFoundError` is caught (`app.py:5534-5537`), so GET and HEAD answer 500 instead of the 422 the PUT twin at least produces a 409 for. One `len(key.encode("utf-8"))` check in the handler closes both.
  - [low] **416 is returned for a syntactically valid multi-range request.** RFC 9110 §14.2 lets a server ignore `Range` or serve the whole representation; `416` is reserved for a range set that is entirely unsatisfiable. `bytes=0-1,4-6` is satisfiable but answered 416 (`app.py:1546-1547`), so range-pipelining clients cannot fall back. (The S3 route rejects it the same way — `web/s3.py:499-515` — so this is consistent within the product but wrong per spec.)
  - [low] **No caching or content-type metadata on the bytes.** No `Cache-Control`/`Expires`, no `Last-Modified`, no `Content-Disposition`, and `Content-Type` is hard-coded `application/octet-stream` (`app.py:5556-5560`); object metadata persisted by an S3 PUT (`ObjectMetadataStore`) is ignored, unlike `web/s3.py:197-222`. Caches may retain authenticated payloads, and a browser cannot display or name a download.
  - [low] **A read is not durably attributable and the log line cannot identify the object.** The audit line carries method, path, IP and key name only (`app.py:1289-1305`); the key is a query parameter, so even that is absent, and no row records the object id, version, bytes served or outcome. After log rotation "who read this object" is unanswerable — notable for a store whose selling point is verified retention.
  - [nit] `_byte_range` (`app.py:1541-1562`) duplicates the S3 `_range` (`web/s3.py:499-515`) with divergent error shapes (JSON 416 + `Content-Range` vs XML `InvalidRange`) and no shared tests; the S3-browser twin `web/app.py:3606-3657` copies the whole streaming/header block, so a fix here will not reach the WebUI download unless applied three times.
  - [nit] Rate limiting exists only on the public share route (`app.py:5577-5592`); there is no per-key read rate or concurrency cap, so one get-scoped key can drive unbounded Telegram downloads (FloodWait risk on the shared USER session, which also serves writes). *Unverified* how Telethon surfaces download-side flood limits.
  - **Verified sound (no finding):** range arithmetic is integer-safe and bounded by `item.size`; absurd integers, `-0`, empty objects, `start >= size`, `end < start` and suffix overflow all resolve to a correct 416 or a clamped whole-object range (probe table above). The requested range is re-validated against the manifest inside the engine (`engine.py:626-627`), and `parts()` resolves dedup aliases and rejects non-contiguous/truncated manifests (`engine.py:648-651, 703-704`), so a short read raises rather than silently returning fewer bytes.
  - **Verified sound (no finding):** HEAD and GET report the same `Content-Length` (`item.size`, `app.py:5515` and `5557`; pinned by `tests/web/test_rest_transfer.py:184`), and HEAD performs no Telegram traffic (pinned at `:177-187`). HEAD's refusal to honour `Range` matches this project's own S3 HEAD (`web/s3.py:3941-3952`), though AWS S3 returns 206 for a ranged HEAD.
  - **Verified sound (no finding):** the object version is pinned before streaming (`item.id` at `app.py:5535`, passed at `5551`), so an overwrite during the transfer cannot mix versions; the response is `StreamingResponse` over the engine's async iterator, never buffered (`app.py:5560`, `engine.py:690,700`), and each chunk is digest-verified before its first byte is yielded (`engine.py:599-609`).
  - **Verified sound (no finding):** no path traversal. `bucket` and `key` are used only in SQL lookups and as header values; scratch file names come from `part.ordinal` (`engine.py:656`), never from user input, and the temporary directory is created by `tempfile` under the configured root. Payload bytes are never logged, and the query string (hence `key`) is not logged either.
  - **Verified sound (no finding):** no data-plane write. Nothing is inserted/updated on `storage_objects` by a read, no Telegram message is sent, and the one DB write a read-only principal can trigger is the API key's own `last_used_at` (`api_keys.py:220-223`), which is expected credential bookkeeping.

  - 409 — generation or object-id precondition mismatch detected at read time (catalog.py:1309-1312, web/app.py:5401-5402); or a key longer than 1024 UTF-8 bytes (verified).
  - 422 — missing `key`, `key` longer than 1024 characters, `generation` < 1 (verified for `generation=0`).
  - 401 / 403 — no bearer (REST); no session or key (admin); API key lacking the scope or route permission; viewer role; missing `x-teledrive-csrf` or cross-origin `Origin` on admin (verified for missing CSRF).
  - 500 — any SQLAlchemy error is uncaught; `remove_current` does not roll back on such a failure.
  - There is no 204, 404, 412 or 410 on any path.
- **Findings:**
  - [critical] **A conditional delete can destroy a different object than the one the client observed (generation ABA).** `remove_current` compares only `generation` (teledrive/storage/catalog.py:1309-1316), and `publish` restarts the counter at 1 whenever the head row is absent (teledrive/storage/catalog.py:1044-1056). An unlink removes the head, so the next upload of the same key is generation 1 again. Verified end-to-end over HTTP: read A at generation 1, `DELETE ...?key=race.bin` (A unlinked), upload B (generation 1, different object id), `DELETE ...?key=race.bin&generation=1` → `200 {"ok": true, "unlinked": true}` and B is gone; the bucket listing is then empty. The response body even exposes the head's object id (`web/app.py:5380-5385`) but the endpoint accepts no id precondition, and `remove_current` already supports `expected_object_id` (catalog.py:1302, 1311-1312) — neither handler passes it. The same ABA applies to conditional REST uploads (`generation` check at web/app.py:5434-5442), so a retry can overwrite a new object too. Fix: accept `If-Match`/`object_id` (or a monotonic per-key generation that survives unlink) and pass it to `remove_current`; S3 already does this (web/s3.py:3585-3589).
  - [high] **Versioned and suspended buckets get no tombstone, notification or history record.** `remove_current` never consults `versioning_state`, unlike `delete_marker`, which creates a tombstone in Enabled buckets and inserts `storage_removed_versions` plus an `s3:ObjectRemoved:Delete` event in Suspended buckets (teledrive/storage/catalog.py:613-698). Verified: after a REST unlink in an Enabled bucket there is no `delete-marker` row, no `storage_removed_versions` row, and no head, while `list_versions` still reports the version (`is_current: false`); in a Suspended bucket the version also stays visible and no removal record is written, contradicting the suspended semantics the S3 path implements. This makes REST deletes invisible to the history page's stated contract ("Every published version and delete marker across all write paths (S3 browser, REST, multipart, copies)", web/static/history.html:120), to notification consumers, and to the metadata journal. It also means an auditor cannot distinguish "never existed" from "unlinked via REST".
  - [high] **The conditional delete's lost race is reported as success.** If the head is overwritten between `get` (catalog.py:1305-1308) and the CAS `DELETE` (1313-1318), rowcount is 0 and the method returns `False` (1320), which both handlers map to `200 {"ok": true, "unlinked": false}` (web/app.py:5403, 3601). A caller that supplied `generation` cannot tell "another writer won, your delete did nothing" from "already gone": the S3 handler raises `PreconditionFailed`/412 in exactly this case (web/s3.py:3590-3594). A 409 is returned only when the mismatch is visible to the initial read, so the status depends on timing. (Race interleaving **unverified**; the zero-row branch is plain code.)
  - [medium] **A legal hold or retention window does not fence the unlink.** Neither handler nor `remove_current` reads `retention_until_ns`/`legal_hold`; `delete_version` does and raises `PermissionError` ("Object is under retention") under the same lock (teledrive/storage/catalog.py:739-747). Verified: with COMPLIANCE retention and legal hold ON, `DELETE ?versionId` refuses while `DELETE /api/v1/buckets/{bucket}/objects?key=...` returns 200 and the key immediately 404s. Bytes are not destroyed by the call itself and GC re-checks the lock (teledrive/storage/gc_collect.py:441-450), so this is not a WORM bypass of physical deletion, but the API silently detaches retained data from its only pointer, and the S3 error the focus asks about (`AccessDenied`) never appears. If "unlink must respect retention" is not the intended contract, it needs to be stated; otherwise it should answer 409/`AccessDenied` like the version path.
  - [medium] **Unlink is the metadata half of physical deletion, and nothing in the response says so.** After the head is gone, `RetainedMediaGC` treats the object as a `deleted` candidate (teledrive/storage/gc_collect.py:178-200) and will delete the Telegram messages once it is older than `DEFAULT_MIN_AGE_SECONDS` = 24 h (gc_collect.py:79) if the owner has enabled GC (gc_collect.py:372-380). Existing tests already assert that an unlinked object is collected (`tests/storage/test_gc_collect.py:87,100`). The REST summary promises "Telegram data retained" (web/app.py:5391), the WebUI confirmation explains the GC caveat (web/static/app.js:856-857, 1001-1002), but an API caller gets only `{"ok": true, "unlinked": true}`: there is no field or status distinguishing "metadata unlinked, bytes retained until GC" from "object destroyed", and the bytes become reclaimable a day later. Operators reading the REST contract either over-estimate (REST users who assume bytes survive) or under-estimate (WebUI users who read the "Delete" label and summary) what happened.
  - [medium] **Public share links survive the unlink and are silently revived by a re-upload.** `share_links` is keyed by `(bucket, object_key)` only, with no object id, version or generation (teledrive/db.py:132-146); `_stream_share` resolves the current head by key at download time (web/app.py:5645) and `admin_create_share` binds the key only (web/app.py:3995-4004). Verified: after an unlink the `/share/<token>` lookup collapses to 404 (web/app.py:5644-5647) and the row remains; re-uploading the same key makes the same token serve the new bytes. That is a credential that outlives the deletion it was scoped to: a link that was dead (and may have been relied on as revoked) becomes a live anonymous download for new content, with its `download_count` already partially consumed by failed attempts (web/app.py:5636-5641).
  - [medium] **Neither handler writes an audit record naming the object.** There is no `_log` in either function, unlike bucket delete (web/app.py:3563-3564), share creation (web/app.py:4006-4007) and credential issuance. The audit middleware records only `DELETE /api/v1/buckets/<bucket>/objects from <ip>` with the actor, because it logs `request.url.path` and never the query string (web/app.py:1289-1305). Verified: after unlinking `audit-me.bin`, the buffer contained exactly the two `[http]` lines and neither mentions the key. So "who deleted which object" cannot be answered; the actor is recorded, the key is not. The key is at least not written to the viewer-readable log either, so this is a gap rather than a leak.
  - [low] **Oversized multibyte keys answer 409, not 422.** Both handlers funnel every `ValueError` — including `_keyhash`'s byte-length rejection (teledrive/storage/catalog.py:148-151) — into 409 (web/app.py:5401-5402, 3599-3600), while the upload path pre-validates the same bound as 422 before staging (web/app.py:5410-5419). Verified: 600 × "é" → 409. A malformed key is not a conflict.
  - [low] **The WebUI summary and button say "Delete" for an unlink.** The route summary is "Delete an object (WebUI)" (web/app.py:3590) and the browser button is "Delete" (web/static/buckets.html:185); only the confirmation dialog and the REST summary (web/app.py:5391) disclose that media is retained. The toast afterwards says "Deleted" (web/static/app.js:1003). The dialog mitigates this for a human, but the terminology invites the exact confusion the focus warns about and contradicts `unlinked` in the body.
  - **Verified sound (no finding):** the delete itself is atomic at the row level (object id and generation are both in the `WHERE`, catalog.py:1313-1318), so it cannot remove a head that changed *after* the CAS starts; `remove_current` returns `False` rather than raising for a missing key, and both handlers return the same 200 for a missing key and a missing bucket (verified), so there is no existence oracle; no bucket row is required, so an unlink cannot resurrect an orphaned bucket; a bucket that still has unlinked history cannot be deleted (409 "Bucket has object history", catalog.py:1329-1343), so the share/alias revival class is confined to same-name object re-uploads, not bucket re-creation; the actor (`user=` / `api-key:<name>`) is captured by the middleware.
- **Tests that should exist:**
  - `test_conditional_unlink_cannot_delete_a_reuploaded_key` — publish A (generation 1), unlink it, publish B (generation 1, different id), then `DELETE ...?key=k&generation=1` must return 409/412 and B must remain readable; today it returns 200 `unlinked: true` and B is gone **(mandatory regression; verified failing today)**.
  - `test_conditional_unlink_race_returns_412_not_200` — monkeypatch the catalog read to return a stale head, run the CAS, assert 412/409 and that the current head survives (today: 200 `unlinked: false`).
  - `test_unlink_in_versioned_bucket_writes_a_tombstone` — in an Enabled bucket, unlink and assert either a `delete-marker` head or a `storage_removed_versions` row exists, that `GET /versions` reports the key as deleted, and that a notification/journal row was written; in a Suspended bucket assert the retired version is recorded.
  - `test_unlink_honours_legal_hold_and_retention` — set legal hold then COMPLIANCE retention on the head, assert the REST unlink returns 409/403 with `AccessDenied`-style detail and that `GET /api/v1/buckets/{bucket}/content?key=...` still serves; then clear both and assert 200.
  - `test_unlink_revokes_or_is_not_revivable_by_share` — create a share for the key, unlink, assert `/share/<token>` is 404, re-upload the same key, then assert the contract: either the link stays 404 (revoked at unlink) or the response warns; do not silently serve the new bytes.
  - `test_unlink_is_audited_with_key_and_actor` — assert exactly one non-`http` line/tuple names the actor and the key, contains no credential material, and is written only after commit.
  - `test_unlink_missing_key_and_unknown_bucket_are_200_noop` — pin the idempotent contract and that both bodies are identical (`{"ok": true, "unlinked": false}`), so neither leaks existence.
  - `test_unlink_rejects_oversized_multibyte_key_with_422` — 600 × "é" must be 422 on both routes, matching the upload path.
- **Verdict:** The row-level CAS is sound and bytes are not touched, but generation reuse lets a stale conditional delete silently destroy a newer object, versioned/suspended buckets get no tombstone or history record, a lost CAS is reported as success, retention does not fence the unlink, share links revive across re-uploads, and no audit line names the key.
