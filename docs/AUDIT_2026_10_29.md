## Real work still open

### A. Bucket delete orphans 13 tables (security, worse than #4 says)

`BucketCatalog.delete_bucket` cleans up only:

```
storage_bucket_tags, storage_bucket_lifecycle, storage_bucket_cors,
storage_pending_tags, storage_website_configs, storage_metadata_configs,
storage_metadata_journal, storage_object_annotations, storage_multipart_uploads
```

It leaves these rows behind:

| Table | Consequence after re-creating a bucket with the same name |
|---|---|
| `storage_bucket_acl_grants` | old grantees silently regain access |
| `storage_object_acl_grants` | same, per key |
| `storage_bucket_policy` | **an old Deny/Allow policy becomes active again** |
| `storage_bucket_abac` | old mandatory tag gates return |
| `storage_bucket_encryption` | stale SSE configuration returns |
| `storage_replication_configs` | deleted bucket's replication resumes |
| `storage_tiering_configs` | old tier rules gate new objects to 403 |
| `storage_notification_configs` / `storage_logging_configs` | events resume to a stale webhook |
| `storage_report_configs` | stale reports regenerate |
| `bucket_quotas` | an old quota silently applies |
| `bucket_account_pins` | objects pinned to an old account |
| `share_links` | **public share URLs keep working for a new bucket's key** |

The review called this "#4 cosmetics/one table"; it is a privilege-revival
bug across the whole governance surface. Priority: high.

### B. MySQL path is still broken in two writes (#8, confirmed)

- `web/app.py:4217` — `INSERT ... ON CONFLICT (bucket) DO UPDATE` (quota
  upsert). PostgreSQL/SQLite syntax only; MySQL errors.
- `web/app.py:4116` — `INSERT OR IGNORE INTO object_content_index` (reindex).

README and CI both list MySQL as supported, so this is a documented promise
the code does not keep.

### C. Two permission catalogs still duplicate the same nine names (#9, confirmed)

`teledrive/api_keys.py::ENDPOINT_PERMISSIONS` (9 entries) and
`web/permissions.py::CURATED_PERMISSIONS` (9 entries) carry the same nine
`rest:*` names with the same values. Not a bug today — they agree — but two
sources for one fact will drift. Collapse to one.

### D. Duplicate function definitions (#15, confirmed)

`teledrive/storage/user_mode.py` defines `_session_from_file_for` **twice**
(lines 51 and 83) and `_session_from_file` (line 46) is never called. The
second definition silently wins.

### E. Schema, indexes, raw SQL

- `#7` schema-init race — being fixed (serialized coordinator + version row).
- `#13` 99 raw `text()` statements in `web/app.py` (users, sessions, quota,
  pin, share) bypass any store layer.
- `#14` 25 tables carry 5 indexes total; `object_aliases.source_object_id`
  (used by GC) is unindexed.

### F. Giant modules (#11, #12 — unchanged)

`web/app.py` ~5 000 lines, `web/s3.py` ~5 000 lines. This is the biggest
maintainability item and the one that makes every other fix riskier.

### G. Docs that are stale

- `docs/METADATA_PARITY_PLAN.md` still has **Phase K (SSE envelope)** as an
  open owner decision. It is moot: SSE-C shipped and `GetBucketEncryption` is
  supported. Envelope encryption remains rejected because it conflicts with
  dedup/replication/content-search — that is a decision, not open work.
- `docs/S3_SPECS.md` engineering checklist (lines 355–361) lists four real
  obligations that are **not** done: exhaustive per-operation matrix
  (normal/auth-fail/malformed/over-limit/retry/race/crash), both-database
  mutation invariants, migration/rollback docs per table, and the rule that
  the matrix is only updated when evidence changes.
- `docs/IMPLEMENTATION_STATUS.md` still carries the physical-GC gates as
  open work; those are owner actions, not engineering tasks, and should say
  so explicitly rather than sit in a checklist next to code work.

## Not work (owner actions, blocked on the real world)

Physical GC authorization requires: an independent backup host, an
authorized 1-hour soak on 2–8 HTTPS endpoints, an original-media recovery
rehearsal with the owner's sealed SQL archive, a legacy cutover decision (or
a signed no-legacy exemption), and independent approvals via
`scripts/ops/verify_production_bundle.py`. None of these can be closed from
a code change; `deletion_permitted` stays `False`.

## Not work (deliberate, permanent)

- `GetObjectTorrent` — needs a BitTorrent swarm and a seeder.
- `WriteGetObjectResponse` — S3 Object Lambda; no Lambda runtime.
- SSE-S3 / SSE-KMS — no server-side key for client-supplied data.
- Requester-pays billing, transfer acceleration — no billing, no edge.

## Order of attack

1. Bucket-delete cleanup (A) — security, small, testable.
2. MySQL writes (B) — documented promise, small.
3. Duplicate catalogs + dead helpers (C, D) — small, prevents drift.
4. Split `web/s3.py` then `web/app.py` (F) — large, do after 1–3 so the
   tests it relies on are stable.
5. Indexes (E/#14) and the store layer for `web/app.py` (E/#13).
6. Docs truth-up (G).
