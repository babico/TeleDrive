# S3 API

The S3 gateway is a second listener in the same process as the Web UI and REST API. It speaks the S3 REST protocol with AWS Signature V4, returns AWS-shaped XML and error codes, and stores object bytes in Telegram while the object graph lives in the same SQL catalog as every other surface. It is not a proxy to AWS and it is not a second database: an object written with `aws s3 cp` is immediately readable in the dashboard and over REST.

The authoritative operation-by-operation matrix is [S3 compatibility](../reference/s3-specs.md). That page is the contract; this page is the practical guide.

## Endpoint and addressing

| Item | Value |
| --- | --- |
| Default endpoint | `http://127.0.0.1:9000` (`TELEDRIVE_S3_PORT`) |
| Addressing style | Path-style: `http://host:9000/<bucket>/<key>` |
| Region | `us-east-1` (equivalent contract) |
| Signing service | `s3` for the general-purpose plane and control plane; `s3express` for directory-bucket zonal operations and CreateSession |
| TLS | Independent `TELEDRIVE_S3_SSL_CERTFILE` / `TELEDRIVE_S3_SSL_KEYFILE` |

Path-style is the documented default and the only style that works without extra DNS. Virtual-hosted addressing exists but is opt-in: the deployment must set `TELEDRIVE_S3_VHOST_SUFFIX` (for example `s3.example.com`), after which a request to `mybucket.s3.example.com` selects `mybucket`. The suffix is validated, and the bucket label is validated with the normal bucket-name rules. Without that variable the `Host` header never selects a bucket.

The `Host` header is part of the SigV4 canonical request. A reverse proxy must preserve the host the client signed (or the client must sign the external name the proxy forwards). If the proxy rewrites `Host` from `s3.example.com` to `127.0.0.1:9000`, the signature will not verify. The same applies to the path: the gateway canonicalizes the raw encoded path byte-for-byte and does not normalize escapes, dot segments or double slashes. Forward the request line unchanged.

`TELEDRIVE_TRUSTED_PROXY` does not relax signing. It only lets the server derive the public origin for presigned URLs generated by the dashboard from `X-Forwarded-Proto`, `X-Forwarded-Host` and `X-Forwarded-Port`. Signature verification still uses the actual `Host`.

The server is single-region. `GetBucketLocation` returns an empty `LocationConstraint`, as AWS does for `us-east-1`. Configure clients with `us-east-1`; there is no multi-region or access-point routing. S3 Express directory buckets are supported as a functional protocol over the same storage (see `docs/reference/s3-specs.md`); the zone id is a logical compatibility label, not an AWS AZ.

## Create S3 credentials

S3 clients do not use dashboard sessions or REST API keys. They need a SigV4 keypair issued from **S3 → Credentials** or through the admin API:

```bash
curl -sS -b td.cookies \
  -H 'X-TeleDrive-CSRF: 1' \
  -H 'Content-Type: application/json' \
  -d '{"name":"restic nightly","permissions":["s3:ListAllMyBuckets","s3:ListBucket","s3:GetBucketLocation","s3:GetObject","s3:PutObject","s3:DeleteObject"]}' \
  http://127.0.0.1:8080/api/v1/admin/s3/credentials
```

The response contains `access_key`, `secret_key`, `id` and the permission list. The secret is returned only here and on rotation.

| Field | Rule |
| --- | --- |
| `name` | 1–120 characters |
| `permissions` | One or more names from the fixed `s3:*` set; unknown names are `422` |
| `expires_at` | Optional Unix seconds, in the future, at most ten years out |

If `permissions` is omitted, the credential gets a read-only default set: `s3:ListAllMyBuckets`, `s3:ListBucket`, `s3:GetBucketLocation`, `s3:GetObject`, `s3:GetObjectAttributes`. Grant more deliberately.

Credential management is an **interactive session** action. An API key is refused even if it holds the route permission, because an S3 credential is itself a secret and the permission list decides what the S3 gateway allows. Existing secrets can be revealed by an admin, but that action is audit-logged; revoked and expired credentials cannot be revealed or edited.

To use the credential you also need a valid S3 master key on the deployment. Secrets are encrypted at rest with it. If the key is missing or invalid, credential creation answers `503` and S3 clients cannot authenticate. See [Encryption](encryption.md) for the key file and Fernet format.

## Signing and presigned URLs

The gateway implements AWS Signature V4 in two forms:

- **Header signing**: `Authorization: AWS4-HMAC-SHA256 Credential=.../date/us-east-1/s3/aws4_request, SignedHeaders=..., Signature=...`.
- **Query presigning**: `X-Amz-Algorithm`, `X-Amz-Credential`, `X-Amz-Date`, `X-Amz-Expires`, `X-Amz-SignedHeaders`, `X-Amz-Signature`.

Rejected by design: SigV2, temporary AWS session tokens (`X-Amz-Security-Token`), unsigned mutable uploads, and any `Authorization` plus query-signature combination. A header-signed request must include a signed `x-amz-date` within a 15-minute clock window; presigned URLs reject a timestamp more than 15 minutes in the future and stop working after their expiry.

Presigned URL lifetime is 1–604,800 seconds (seven days), and every returned URL is passed through the same verifier. A **presigned GET** signs only the host and uses `UNSIGNED-PAYLOAD`, so it works like an AWS presigned download. A **presigned PUT** must bind a SHA-256 checksum in the signed headers; a bare presigned PUT that could replace an object with arbitrary bytes is refused. A presigned `CopyObject` must likewise sign the source header and the empty-body digest.

Browser `POST` form uploads are supported only within a restricted SigV4 policy: 20 MiB form limit, policy expiry at most 15 minutes from signing, checksum-pinned, and a bounded set of form fields. They are not arbitrary AWS POST policies.

The dashboard's **Link** button is the simplest way to produce a working presigned GET: it signs server-side with an active credential that holds `s3:GetObject`, so no secret reaches the browser.

## Client setup

### AWS CLI

```bash
aws configure set aws_access_key_id 'TDXXXXXXXXXXXXXXXXXXXXXXXX'
aws configure set aws_secret_access_key 'YOUR_SECRET'
aws configure set default.region us-east-1
aws configure set default.s3.addressing_style path

aws --endpoint-url http://127.0.0.1:9000 s3api create-bucket --bucket backups
aws --endpoint-url http://127.0.0.1:9000 s3 ls s3://backups
```

Use `--endpoint-url` on every command (or an alias). `default.s3.addressing_style path` avoids virtual-host attempts against an endpoint that is not DNS-configured for bucket subdomains.

### boto3

```python
import boto3
from botocore.config import Config

s3 = boto3.client(
    "s3",
    endpoint_url="http://127.0.0.1:9000",
    aws_access_key_id="TDXXXXXXXXXXXXXXXXXXXXXXXX",
    aws_secret_access_key="YOUR_SECRET",
    region_name="us-east-1",
    config=Config(s3={"addressing_style": "path"}, signature_version="s3v4"),
)

s3.create_bucket(Bucket="backups")
s3.put_object(Bucket="backups", Key="hello.txt", Body=b"hello\n")
print(s3.get_object(Bucket="backups", Key="hello.txt")["Body"].read())
for page in s3.get_paginator("list_objects_v2").paginate(Bucket="backups"):
    print([item["Key"] for item in page.get("Contents", [])])
```

### rclone

```bash
rclone config create td s3 \
  provider Other \
  access_key_id 'TDXXXXXXXXXXXXXXXXXXXXXXXX' \
  secret_access_key 'YOUR_SECRET' \
  endpoint 'http://127.0.0.1:9000' \
  region us-east-1 \
  force_path_style true

rclone lsd td:
rclone copy ./local-dir td:backups/local-dir --progress
```

rclone's S3 backend performs several probe requests at startup. The gateway answers the optional read-only probes with valid AWS shapes and rejects configuration attempts it cannot honour instead of pretending.

## Quickstart

```bash
ENDPOINT=http://127.0.0.1:9000
BUCKET=backups

# 1. Create the bucket (idempotent for an existing owned bucket)
aws --endpoint-url "$ENDPOINT" s3api create-bucket --bucket "$BUCKET"

# 2. Put and get a small object
aws --endpoint-url "$ENDPOINT" s3 cp ./hello.txt "s3://$BUCKET/hello.txt"
aws --endpoint-url "$ENDPOINT" s3 cp "s3://$BUCKET/hello.txt" ./hello.copy

# 3. List
aws --endpoint-url "$ENDPOINT" s3 ls "s3://$BUCKET" --recursive

# 4. Multipart: the CLI switches automatically above its threshold
aws --endpoint-url "$ENDPOINT" s3 cp ./large.bin "s3://$BUCKET/large.bin"

# 5. Presigned GET, valid for one hour
aws --endpoint-url "$ENDPOINT" s3 presign "s3://$BUCKET/hello.txt" --expires-in 3600
```

Explicit multipart is the standard three-step API:

```bash
UPLOAD_ID=$(aws --endpoint-url "$ENDPOINT" s3api create-multipart-upload \
  --bucket "$BUCKET" --key huge.bin --query UploadId --output text)

aws --endpoint-url "$ENDPOINT" s3api upload-part \
  --bucket "$BUCKET" --key huge.bin --part-number 1 \
  --upload-id "$UPLOAD_ID" --body part1.bin

aws --endpoint-url "$ENDPOINT" s3api complete-multipart-upload \
  --bucket "$BUCKET" --key huge.bin --upload-id "$UPLOAD_ID" \
  --multipart-upload '{"Parts":[{"PartNumber":1,"ETag":"\"...\""}]}'
```

Every non-final part must be at least 5 MiB, part numbers run 1–10,000, and completion publishes the already-staged parts without re-uploading them. A failed or abandoned upload leaves its Telegram chunks as a recovery journal; physical GC is the only thing that deletes them, and it is owner-gated.

## Consistency and integrity

- **One catalog.** Publish is one SQL transaction on a version head. Once a `PUT` returns, the object is visible to S3, REST, the dashboard and version listings. Concurrent writers are serialized by generation checks; there is no eventual-consistency window inside the deployment.
- **ETag.** For a single `PUT`, the ETag is the quoted SHA-256 of the plaintext object, not an MD5. Multipart objects have their own ETag representation. Never compare a TeleDrive ETag to an AWS MD5 ETag.
- **Checksums.** Uploads are verified before publication: signed SHA-256, SHA-1, `Content-MD5`, CRC32, CRC32C and CRC64NVME are checked on the implemented PUT and UploadPart paths. `x-amz-checksum-mode: ENABLED` on an object GET/HEAD returns the immutable full-object SHA-256; `GetObjectAttributes` exposes the same digest with `FULL_OBJECT` semantics.
- **Reads.** Bytes are read from Telegram and verified against the manifest before they are streamed. An encrypted object is authenticated per chunk before decryption.
- **Conditional requests.** `If-Match` and `If-None-Match` work for object GET/HEAD and for bounded simple PUT/DELETE and multipart completion. Date-based write preconditions and conditional explicit-version deletes are rejected with `501` rather than ignored.
- **Versioning.** `Enabled` creates a new version on every write and delete markers on delete; `Suspended` replaces the current version and deletes the head without a marker. History remains readable.

## Limits and quotas

| Limit | Value |
| --- | --- |
| Single request body | 2 GiB default (`web.rest_max_upload_bytes`); `0` disables REST/S3 uploads |
| Multipart parts | 10,000 numbered parts; 5 MiB minimum for every non-final part |
| List page | `max-keys` 1–1000 |
| ListBuckets page | `max-buckets` 1–10,000 |
| Object user metadata | 2 KiB serialized |
| Object tags | 10 per version; 128-byte keys, 256-byte values |
| Bucket tags | 50 per bucket |
| Object annotations | 50 per object; 128-byte name, 1 KiB value |
| Bucket CORS | 100 rules, 64 KiB document |
| Bucket policy | 20 KiB, 50 statements |
| Presigned expiry | 1–604,800 seconds |
| Browser POST form | 20 MiB; policy ≤15 minutes |
| `SelectObjectContent` | 256 MiB scan, 64 MiB response, 1 MiB per event |
| Bucket quota | Optional; breach answers `413 EntityTooLarge` |

The 2 GiB body cap is a configuration ceiling, not a promise that Telegram will accept a file of that size. Telegram's own per-file and per-account limits still apply, and a FloodWait or oversized send surfaces as a failed request or job.

Per-bucket quotas are not an AWS feature; they are enforced by TeleDrive on S3 uploads, REST uploads, copies and durable local jobs.

## Encryption

Three states exist:

| Mode | How it is selected | Who holds the key |
| --- | --- | --- |
| None (default) | No header, no bucket default | Nobody; Telegram stores plaintext |
| SSE-C | Per request, three customer-key headers | The client; the key is never stored |
| SSE-S3 envelope | `storage.encryption: envelope` plus a bucket `AES256` default or `x-amz-server-side-encryption: AES256` | The deployment, via the S3 master key |

`aws:kms` is always rejected with `501`; there is no KMS. Asking for `AES256` while `storage.encryption` is `none` is `501` naming the setting, never a silent plaintext write. SSE-C reads require the same customer key; a missing or wrong key is `400 InvalidRequest` before any plaintext is emitted, and REST/WebUI reads of SSE-C objects are refused for the same reason.

Envelope encryption disables deduplication, replication and content indexing for encrypted objects. The full trade-off, key management and failure modes are in [Encryption](encryption.md).

## Unsupported operations and honest refusals

Two AWS operations are permanently unsupported and refuse by name:

| Operation | Why |
| --- | --- |
| `GetObjectTorrent` | There is no BitTorrent seeder; the bytes live in Telegram |
| `WriteGetObjectResponse` | There is no S3 Object Lambda runtime |

Everything else in the 116-operation inventory is supported for the documented contract, but a supported operation can still refuse an unsupported *variant*. The common honest refusals:

- `501 NotImplemented` for SSE-KMS, date-based write preconditions, `RedirectAllRequestsTo` and `RoutingRules` in website configuration, SQS/SNS/Lambda notification destinations, Parquet/ORC report formats, `Requester` request payment, `Enabled` transfer acceleration, MFA delete, and email/group/public ACL grantees.
- `403 InvalidObjectState` for `RestoreObject` on an object that is already immediately readable, and for an archived object before its restore window opens.
- Real S3 Express directory-bucket sessions: `CreateSession` issues short-lived bucket-scoped credentials (token hashed at rest, secret encrypted with the server master key, immediate SQL revocation), and `ListDirectoryBuckets` enumerates actual directory buckets with opaque-token pagination.
- `400` for unknown selectors and ambiguous parameters; an unsupported selector never degrades into an ordinary GET/PUT/DELETE.

A 501 is the design, not a missing handler: acknowledging encryption, retention, a public ACL or a storage class without implementing its semantics would mislead a backup client.

## What is different from AWS

| Area | TeleDrive behaviour |
| --- | --- |
| Storage class and tiering | One real tier. `STANDARD` is the only accepted class. Intelligent-Tiering is stored, and its `ARCHIVE_ACCESS`/`DEEP_ARCHIVE_ACCESS` state is an access gate in this catalog that makes reads answer `403 InvalidObjectState` until restored. Telegram bytes never move |
| Deletion | Logical by default. Delete markers and version revocation remove visibility; the Telegram media remains until an owner enables physical GC and runs a collection |
| Key management | No AWS KMS. SSE-C is client-held; envelope encryption uses a deployment master key |
| Replication | The destination is a configured TeleDrive Telegram account label, not an ARN or another AWS bucket. One replica per chunk, so enabled prefixes must not overlap |
| Bucket policies and ACLs | Real evaluation, but principals are TeleDrive access keys. `*`, AWS accounts, services and federated principals are rejected. Private-only: no anonymous object path |
| Public access | Only the explicit website `public_read` admin decision publishes objects, at `/site/{bucket}/`; the S3 public-access-block flags and policy-status scan stay private |
| ETag | SHA-256 for a single PUT, never an MD5 |
| Region and location | Single-region `us-east-1`; empty `LocationConstraint`; no multi-region or access points |
| Reports | Analytics and metrics are JSON Lines/JSON; inventory is gzip CSV with the AWS column shape. Parquet and ORC are `501` |
| Notifications | An owner-allowlisted HTTP(S) webhook with a durable outbox and retries, not SQS/SNS/Lambda |
| S3 Express and Object Lambda | Directory buckets are a functional protocol over the same storage: real session credentials, zonal `s3express` signing, logical-zone labels — no AWS AZ/One Zone durability or Express throughput. No Lambda runtime: `WriteGetObjectResponse` is one of the two permanent unsupported operations |
| Billing and requester pays | No AWS billing. `BucketOwner` is the only payer state; `Requester` is `501` |

Latency is dominated by Telegram, not by S3 semantics. A first read of a large object may take seconds to minutes depending on chunk retrieval and FloodWait; a metadata-only HEAD is a SQL lookup. Design clients with retries and timeouts that tolerate this, and prefer the S3 gateway for bulk transfers and the REST API for control-plane work.

For per-operation status, evidence and the exact accepted parameters, read [S3 compatibility](../reference/s3-specs.md) before relying on an advanced feature.
