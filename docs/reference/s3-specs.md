# S3 API Specifications and Compatibility Matrix

> **Scope:** TeleDrive's S3-compatible listener over the shared SQL catalog and USER MTProto engine with historical same-channel Bot-media reads only, **not** AWS S3. **Last reviewed:** 2026-11-06 against the development default branch. **Target:** P2 Advanced S3 planning; this document does not assert production certification or update the released v1.0.10 binary.
>
> **Canonical operation inventory:** [AWS S3 REST API, 2006-03-01, operation list](https://docs.aws.amazon.com/AmazonS3/latest/API/API_Operations_Amazon_Simple_Storage_Service.html). This matrix enumerates **all 116 operations** on that AWS S3 service-reference page as reviewed. AWS S3 Control, S3 Tables, S3 on Outposts, S3 Files and future additions are **separate services**, not silently included in this list. This is a protocol/API coverage inventory, not a claim to implement every possible request parameter, header, mode or AWS service.

## 1. Read the status correctly

| Status | Meaning |
| --- | --- |
| ✅ Supported | Implemented for the explicitly documented TeleDrive contract and backed by focused regression coverage; **not** a claim of complete AWS parity. |
| 🟡 Partial | Route/behavior exists, but significant AWS options, response fields or state transitions are deliberately restricted. Treat unsupported variants as unsupported. |
| ❌ Unsupported | No supported TeleDrive contract; do not rely on that AWS method. It may be rejected as NotImplemented (501) **or** require additional fail-closed routing tests; do not assume every selector currently returns the same error. |
| Not verified | Client, deployment configuration or optional parameter is untested; never upgrade an operation's status merely because another client happens to succeed. |

**Inventory totals:** 114 supported, 0 partial (0 by code, 0 by design), 2 unsupported; **116 AWS S3 operations**. Count operations, not request permutations. Partial operations are **not** fully supported; section 3 classifies each partial by *why* it is partial. These statuses describe development code and tests, not a fresh CI run or independently validated production setup.

**Machine-readable inventory:** [116-operation JSON manifest](https://github.com/babico/TeleDrive/blob/main/teledrive/s3/operation_manifest.json) is checked against every row of this matrix in [fail-closed route tests](https://github.com/babico/TeleDrive/blob/main/tests/s3/test_s3_route_guard.py). Supported AWS subresources are explicitly allowlisted before the signer, SQL and Telegram transports can mutate data; unknown selectors cannot silently become normal bucket/object operations. This addresses a P2-0 subtask, **not** the entire protocol parity gate.

**Implementation evidence:** [gateway router](https://github.com/babico/TeleDrive/blob/main/web/s3.py), [S3 protocol modules](https://github.com/babico/TeleDrive/tree/main/teledrive/s3), [S3 tests](https://github.com/babico/TeleDrive/tree/main/tests), [CI guide](ci.md), [implementation/production status](../project/status.md). On a new code SHA, rerun its own CI rather than recycling a historical green status. No new test execution was performed solely to prepare this inventory.

### Quotas

Each bucket can carry an optional per-bucket quota: a maximum total size in bytes and/or a maximum object count. Quotas are enforced server-side on upload through both the S3 gateway and the REST API, and are configurable via the admin API (`GET`/`PUT /api/v1/admin/storage/buckets/{bucket}/quota` with `max_size_bytes` and `max_objects`; `null` disables a limit) or the Web UI **S3** page. Uploads that would exceed either limit are rejected.

## 3. Implemented and partially implemented AWS S3 actions

Every qualification below is part of the contract. Partial operations are
classified by **why** they are partial:

- **Partial — by code**: a genuinely closeable gap. The missing piece is
  implementable within the current architecture; it is tracked work, not a
  decision. Closing one is a normal feature increment.
- **Partial — by design**: the "gap" is a deliberate architectural decision —
  the immutable private-only model, owner-gated physical Telegram deletion,
  or AWS-external semantics that cannot honestly exist over Telegram.
  "Implementing" these would mean faking AWS behavior the platform does not
  have, so they stay fail-closed on purpose.

The [machine-readable manifest](https://github.com/babico/TeleDrive/blob/main/teledrive/s3/operation_manifest.json)
carries each partial's `gap_class` and is synchronized with this table by CI.

Non-empty parts answer `206` with `Content-Range` and suppressed checksums; a zero-byte part answers an empty `200` without `Content-Range`; `x-amz-mp-parts-count` is returned only when `partNumber` was requested and the object was uploaded as a multipart upload; a single-PUT object is its own part 1. Sparse completions position a part by the stored sizes of the prior parts in completion order, not part-number arithmetic. `HEAD ?partNumber` remains rejected with `501` until independently specified, and SSE-C multipart objects fail closed on part reads because their layout ETag record is not verifiable. SSE-C objects require the same customer key on every read: a missing or wrong key is `400 InvalidRequest` before any plaintext is emitted, each overlapping chunk is GCM-authenticated before decryption, and the response never advertises a plaintext checksum or plaintext ETag. Envelope objects are unwrapped with the deployment master key and report `x-amz-server-side-encryption: AES256`; a replaced master key fails closed with a named error rather than returning garbage. No archive/SSE-KMS storage classes exist; those requests are rejected rather than emulated. |
| [HeadObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html) | ✅ Supported | Object metadata and selected VersionId/read preconditions. SSE-C HEAD verifies the key against the stored non-secret key-MD5 fingerprint and returns the AWS SSE-C response headers (algorithm + key MD5) without ever returning the key. Absent AWS headers describe features that do not exist here. |
| [CreateMultipartUpload](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CreateMultipartUpload.html) | ✅ Supported | Signed initiation with selected metadata. With SSE-C headers the upload is bound to that key fingerprint: every UploadPart, ListParts and CompleteMultipartUpload must present the same key or fails with `400 InvalidRequest`. | [GetBucketRequestPayment](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetBucketRequestPayment.html) | ✅ Supported | Returns the exact stored payer as AWS-shaped XML (`<Payer>BucketOwner</Payer>` for every bucket, because no requester-pays billing exists here). | [CreateSession](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CreateSession.html) | ✅ Supported | Issues real, cryptographically random short-lived credentials for an existing directory bucket: `AccessKeyId`, `SecretAccessKey`, `SessionToken` and `Expiration` bound to exactly ONE bucket, a mode (`ReadOnly`/`ReadWrite`, default `ReadWrite`), the signing long-lived access key and the bucket's logical zone. Default 5-minute lifetime, like AWS. The token is stored only as a SHA-256 hash; the secret is Fernet-encrypted with the S3 master key; revocation (bucket deletion or owner-credential revocation) is immediate and durable. The control plane keeps long-lived credentials under the real `s3express` SigV4 scope; failure taxonomy: malformed name `400 InvalidBucketName`, an existing general-purpose bucket `400 InvalidRequest`, any other well-formed name `404 NoSuchBucket`. **Honesty note:** this is the functional S3 Express session protocol over Telegram storage, not AWS S3 Express One Zone hardware, latency or durability. |

> **Journal actor field.** Rows written by object tagging, annotation, ACL and rename record the acting access key. Rows written by internal catalog operations (publish, delete marker, version revocation, multipart completion) record an empty actor rather than a guessed one — the catalog layer does not know which credential a background scheduler or GC pass belongs to. An empty actor means "not attributed", never "anonymous".

## 4. Unsupported AWS S3 actions grouped for the roadmap

**Only the operations actually listed below remain unsupported.** The
P2 groups are retained as a history of the workstreams that shipped; their
operation tables are deliberately empty because none of those operations
is unsupported any more. An operation is never implied to work by a
similarly named REST admin endpoint or internal SQL function, and the two
P3-H rows are the complete unsupported set in the reference inventory.

### P2-C — Access control, ACLs, policies and ownership

**Status: shipped.** The real bucket-policy engine, ACL grant store and
ownership/ABAC controls described in section 3.1 are implemented: JSON
policies evaluate per request against credential principals, Deny wins, an
explicit Allow short-circuits the ACL layer, and the ACL gate is a
fail-closed intersection with the credential's own scopes. Email/group/
public principals and `*`/AWS/Service/Federated policy principals remain
rejected, so the private-only line is unchanged.

No operation in this group is unsupported.

### P2-B — Encryption and immutable retention

**Status: shipped.** Bucket encryption round-trips SSE-C (empty rule set)
and when `storage.encryption: envelope` is configured, an AES256 default

backed by a deployment master key with per-object data keys. Object
Lock/retention/legal-hold are real per-version state enforced on explicit,
batch, suspended-overwrite and copy-overwrite deletes, with COMPLIANCE
immutable in the catalog layer. `aws:kms` stays 501 because there is no
KMS. Envelope objects are excluded from content-addressed dedup,
replication and the plaintext index — the documented trade-off.

No operation in this group is unsupported.

### P2-D — Lifecycle, expiration, transitions, replication and restore

**Status: shipped.** Lifecycle rules (abort, expiration, transitions,
noncurrent-version expiration/transitions), the S3 replication
configuration surface and RestoreObject all exist. Replication maps onto
the existing storage-engine cross-account runtime; archive transitions
queue a verified cold copy; RestoreObject opens a real retrieval window
when a cold archive exists and the immediate hot-copy window otherwise.
Physical expiration/deletion remains GC-gated and owner-approved (see
section 3.3), and no AWS retrieval-speed SLA is implied.

No operation in this group is unsupported.

### P2-E — Advanced data-plane protocol compatibility

**Status: shipped.** No unsupported operations remain in this group.
UploadPartCopy (inclusive copy-source ranges), ranged CopyObject,
presigned CopyObject, completion checksum composition (COMPOSITE and
FULL_OBJECT), version-listing selectors and the get-part read contract are
implemented; section 3.2 records that no by-code partial remains.

### P2-F — Website, notifications and access logging

**Status: shipped.** Website configuration stores index/error documents
and the anonymous `/site/{bucket}/` route stays inert until an admin turns
on `public_read`. Notifications use an owner-allowlisted HTTP(S) webhook
with a transactional outbox, exponential backoff and HMAC signing.
Access-logging configuration round-trips; delivery itself is still a
documented scheduled gap rather than instant AWS log delivery.

No operation in this group is unsupported.

### P3-G — Analytics, inventory, metrics and tier policies

**Status: shipped.** Analytics, inventory and metrics configuration CRUD
and the report runner exist: analytics writes JSON Lines, inventory writes
gzip CSV with the AWS column shape, and metrics writes a JSON object into
the destination. Intelligent-Tiering stores a bounded document and a
scheduler transitions the catalog `storage_class` from real access
timestamps; the tier is an access gate over Telegram bytes, not AWS
Glacier or a physical storage class.

No operation in this group is unsupported.

### P3-H — Remaining AWS-managed products and provider services

**Status: partially shipped.** The functional directory-bucket/Express
session protocol, S3 Metadata configuration, request-payment and
accelerate states, RenameObject and SelectObjectContent are implemented
(section 3.1). Two AWS services have no honest Telegram mapping and stay
unsupported: an Object Lambda payload runtime (`WriteGetObjectResponse`)
and a BitTorrent seeder (`GetObjectTorrent`). S3 Express here remains a
protocol over Telegram, not AWS One Zone hardware or latency.

| AWS S3 API operation | Status | Target |
| --- | --- | --- |
| [GetObjectTorrent](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObjectTorrent.html) | ❌ Unsupported | P3-H |

## 6. Release and evidence boundaries

A successfully parsed or authenticated AWS request is **not** automatically a supported S3 specification. Successful synthetic tests prove only their scenario, not general AWS service parity, multi-region behavior, original-media recovery or an operator-authorized production cutover. P2 work should preserve the default **one-container** interface topology, bounded resource use, shared REST/S3/local-job catalog, and fail-closed safety guarantees documented in [Project Status](../project/status.md).

**Upstream reference:** [Amazon S3 REST API operations](https://docs.aws.amazon.com/AmazonS3/latest/API/API_Operations_Amazon_Simple_Storage_Service.html). **Repository evidence:** [S3 route](https://github.com/babico/TeleDrive/blob/main/web/s3.py), [S3 modules](https://github.com/babico/TeleDrive/tree/main/teledrive/s3), [S3 tests](https://github.com/babico/TeleDrive/tree/main/tests), [TODO](../project/roadmap.md). The AWS operation inventory can grow; re-audit it before every advanced-compatibility milestone.
